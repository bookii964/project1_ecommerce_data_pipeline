# 데이터 사전 & 정제 규칙서 — product_catalog

> **이 문서의 역할**
> 1단계 프로파일링에서 "실제로 어떤 값이 들어있는지"를 관찰했다.
> 이 문서는 그 관찰을 근거로 **"어떤 값이 정상인가"를 확정**하는 문서다.
> 앞으로 3단계(비정상 색출)와 4단계(정제)는 전부 이 문서의 규칙을 기준으로 판정한다.
> 정제 결과에 의문이 생기면 코드가 아니라 이 문서를 먼저 확인하면 된다.
>
> 대상 파일 : `01_raw/product_catalog_dirty_30pct.csv`
> 전체 규모 : 500행 × 4열

---

## 1. 테이블 개요

상품 마스터 테이블. 판매 상품 1건이 1행에 해당한다.
`orders` 테이블이 `product_id`로 이 테이블을 참조하므로, **`product_id`는 절대 훼손되면 안 되는 핵심 키**다.

| 컬럼명 | 의미 | 역할 |
|---|---|---|
| product_id | 상품 고유번호 | 기본키(PK) |
| product_name | 상품명 | 속성 |
| category | 상품 분류 | 분석 기준 축 |
| price | 판매 단가 | 수치 분석 대상 |

---

## 2. 컬럼별 정상 규칙

### 2-1. product_id

| 항목 | 내용 |
|---|---|
| 자료형 | 문자열 |
| 형식 | `PROD-` + 숫자 4자리 (예: `PROD-0001`) |
| 결측 허용 | 불가 |
| 중복 허용 | 불가 (기본키) |
| 1단계 검사 결과 | **위반 0건 — 정상** |

→ 정제 대상 아님. 다만 다른 컬럼을 고칠 때 이 값이 바뀌지 않았는지 검증용으로 사용한다.

---

### 2-2. product_name

| 항목 | 내용 |
|---|---|
| 자료형 | 문자열 |
| 형식 | 영문 단어의 조합, 각 단어 첫 글자 대문자 (Title Case) |
| 결측 허용 | 불가 |
| 중복 허용 | 가능 (동명 상품이 있을 수 있음) |

**발견된 오염 유형 (총 4가지)**

| 유형 | 건수 | 예시 | 처리 방침 |
|---|---|---|---|
| ① 앞뒤 공백 | 37건 | `' Bit Its'`, `'Section Drive '` | **자동 수정** — 공백 제거 |
| ② 대소문자 불일치 | 35건 | `'MEAN YOUR'`, `'current agreement'` | **자동 수정** — Title Case 통일 |
| ③ 단어 사이 공백 누락 | 23건 | `'StartWear'`, `'BringOffice'` | **자동 수정** — 소문자+대문자 사이에 공백 삽입 |
| ④ 문자 중복 오타 | 11건 | `'Beaautiful'`, `'Speaak'` | **자동 수정** — 모음 중복(aa, ii, uu 등) 1개로 축소 |
| ⑤ 끝에 숫자 붙음 | 19건 | `'Health6'`, `'Employee7'` | **보류 후 플래그** — 아래 설명 참고 |

**⑤를 자동 수정하지 않는 이유**
상품명에 숫자가 붙는 것은 오염일 수도 있지만 실제 모델명일 수도 있다(예: iPhone 15).
정답을 알 수 없는 상태에서 지우면 정보를 잃는다.
→ **원본 값을 그대로 두고, `name_flag` 컬럼에 `숫자포함_확인필요`로 표시만 한다.**
→ 실무에서 현업 담당자에게 확인 요청할 목록이 되며, 이 판단 과정 자체가 포트폴리오의 근거 자료가 된다.

**④에서 자음 중복(ll, ss, tt)을 건드리지 않는 이유**
영어 단어에는 자음 중복이 정상적으로 존재한다(`Small`, `Address`).
전부 고치면 정상 단어를 망가뜨린다.
→ 영어에서 거의 나타나지 않는 조합(`aa`, `ii`, `uu`, `jj`, `kk`, `vv`, `ww`, `yy`, `hh`, `qq`, `xx`, `zz`)만 대상으로 한다.

### 2-3. category

| 항목 | 내용 |
|---|---|
| 자료형 | 문자열 |
| 허용값 | `automotive` / `beauty` / `clothing` / `electronics` / `home` / `kitchen` / `sports` / `toys` **8종만 허용** |
| 표기 | 전부 소문자 |
| 결측 허용 | 불가 (30건 존재 → 처리 필요) |

**현황** : 원본에 46종의 값이 존재 → 8종으로 정리해야 함

**발견된 오염 유형 (총 5가지)**

| 유형 | 예시 | 변환 방법 |
|---|---|---|
| ① 앞뒤 공백 | `'kitchen '`, `'beauty '` | 공백 제거 |
| ② 대문자 표기 | `'KITCHEN'`, `'SPORTS'` | 소문자 변환 |
| ③ 끝에 특수문자 | `'clothing-'`, `'home_'` | 끝의 `-`, `_` 제거 |
| ④ 숫자 치환(리트체) | `'3l3ctronics'`, `'hom3'`, `'b3auty'` | 숫자 `3` → 문자 `e` 로 복원 |
| ⑤ 3글자 축약 | `'clo'`, `'kit'`, `'aut'`, `'bea'`, `'ele'`, `'hom'`, `'toy'` | 앞글자 일치하는 정상값으로 복원 |

**변환 순서 (순서가 중요하다)**

```
원본  →  ① 앞뒤 공백 제거
      →  ② 소문자 변환
      →  ③ 끝의 -, _ 제거
      →  ④ 3 → e 치환
      →  ⑤ 8종 정상값과 대조, 없으면 앞글자 매칭으로 축약형 복원
```

순서를 지켜야 하는 이유: `'KITCH3N '` 같은 값은 공백·대문자·숫자치환이 **동시에** 걸려 있다.
한 단계씩 벗겨내야 최종적으로 `kitchen`에 도달한다.

**⑤ 축약형 복원의 안전성 검증 (중요)**
축약형을 앞글자로 매칭할 때 **후보가 2개 이상이면 잘못 복원할 위험**이 있다.
실제로 확인한 결과 7개 축약형 모두 후보가 정확히 1개씩이었다.

| 축약형 | 매칭 후보 | 판정 |
|---|---|---|
| aut | automotive | 유일 ✅ |
| bea | beauty | 유일 ✅ |
| clo | clothing | 유일 ✅ |
| ele | electronics | 유일 ✅ |
| hom | home | 유일 ✅ |
| kit | kitchen | 유일 ✅ |
| toy | toys | 유일 ✅ |

→ **자동 복원해도 안전하다.** (만약 후보가 2개였다면 자동 변환을 포기하고 플래그 처리했어야 한다)

**결측 30건 처리**
→ **`unknown`으로 채운다.** 행을 삭제하지 않는다.
→ 이유: 해당 행의 `product_id`와 `price`는 정상값이라 삭제하면 멀쩡한 데이터까지 잃는다.
   또한 `orders` 테이블이 이 `product_id`를 참조하므로 삭제 시 조인이 깨진다.

### 2-4. price

| 항목 | 내용 |
|---|---|
| 자료형 | 숫자 (소수점 2자리) |
| 허용 범위 | 0보다 큰 값 |
| 결측 허용 | 불가 (26건 존재) |

**발견된 오염 유형 (총 5가지)**

| 유형 | 건수 | 예시 | 처리 방침 |
|---|---|---|---|
| ① 앞뒤 공백 | 다수 | `' 32309.95'` | 자동 수정 — 공백 제거 |
| ② 천단위 쉼표 | 다수 | `'1,200'` | 자동 수정 — 쉼표 제거 |
| ③ 소수점 자릿수 불일치 | 다수 | `'2215.4'`, `'0'` | 자동 수정 — 소수점 2자리로 통일 |
| ④ 음수 | 26건 | `-100` | **결측(NULL) 처리** |
| ⑤ 0원 | 19건 | `0` | **결측(NULL) 처리** |

**③이 '오염'이 아닌 이유 (중요한 구분)**
1단계 검사에서 167건이 걸렸지만, 그중 대부분은 `2215.4`처럼 **값 자체는 정상인데 표기만 다른** 경우다.
데이터가 틀린 게 아니라 형식이 통일되지 않은 것이므로, **오염이 아니라 표준화 대상**으로 분류한다.
→ 3단계 집계에서 '오염 건수'와 '표준화 건수'를 분리해서 세야 리포트가 정확해진다.

**④ 음수 `-100`이 26건 전부 동일한 값인 점**
값이 전부 정확히 `-100`이다. 이는 실제 가격이 아니라 **시스템이 값을 못 채웠을 때 넣는 대체값(sentinel)** 일 가능성이 높다.
→ 실질적으로는 결측이므로 NULL로 바꾼다. 0원도 판매가로 성립하지 않으므로 동일 처리.
→ NULL 처리 후 `price_flag` 컬럼에 원인(`음수대체값` / `0원`)을 기록해 추적 가능하게 남긴다.

**극단값(이상치) 판단 — 삭제하지 않음**

| 지표 | 값 |
|---|---|
| 중앙값 | 21,318 |
| 75% 지점 | 36,761 |
| IQR 상한 (Q3 + 1.5×IQR) | 82,971 |
| 상한 초과 | 11건 (최대 851,374) |

→ **값을 건드리지 않고 `price_flag`에 `고가이상치_확인필요`로 표시만 한다.**
→ 이유: 고가 상품이 실제로 존재할 수 있다. 정답을 모르는 상태에서 지우면 **매출 분석 결과가 왜곡된다.**
→ 통계적으로 튄다는 것과 틀렸다는 것은 다르다. 판단 근거를 남기고 유지하는 것이 안전하다.

## 3. 정제 후 산출물 형태

`03_cleaned/product_catalog_cleaned.csv` — 원본 4개 컬럼 + 추적용 2개 컬럼

| 컬럼 | 설명 |
|---|---|
| product_id | (변경 없음) |
| product_name | 정제 완료 |
| category | 8종 + `unknown` |
| price | 숫자, 소수점 2자리, 비정상은 빈 값 |

| price_flag | 사람 확인이 필요한 가격 사유 |

**플래그 컬럼을 남기는 이유**
정제는 "고친 것"뿐 아니라 "고치지 않기로 판단한 것"도 기록해야 완성된다.
나중에 이 파일만 봐도 어떤 값이 왜 그대로 남았는지 알 수 있다.

## 4. 처리 방침 요약

| 방침 | 적용 대상 | 근거 |
|---|---|---|
| **자동 수정** | 정답이 명확한 것 (공백·대소문자·특수문자·숫자치환·축약형) | 복원 결과가 유일하게 결정됨 |
| **NULL 처리** | 값이 논리적으로 불가능한 것 (음수 가격, 0원) | 유지하면 평균·합계 계산이 오염됨 |
| **대체값 입력** | 분류 결측 (`unknown`) | 행을 살려야 조인이 유지됨 |
| **플래그만** | 정답을 알 수 없는 것 (숫자 상품명, 고가 이상치) | 임의 판단은 데이터 왜곡 위험 |
| **행 삭제** | 해당 없음 | product_id가 다른 테이블에서 참조되므로 삭제 불가 |

> **원칙** : 확신 없이 지우지 않는다. 지우는 대신 표시하고 근거를 남긴다.
