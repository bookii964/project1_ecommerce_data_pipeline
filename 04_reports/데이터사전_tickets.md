# 데이터 사전 & 정제 규칙서 — support_tickets_30000

> **이 문서의 역할**
> 1단계 프로파일링 결과를 근거로 "어떤 값이 정상인가"를 확정한다.
>
> 대상 파일 : `01_raw/support_tickets_30000_dirty.csv`
> 전체 규모 : 30,000행 × 8열
>
> **앞선 파일들과의 차이**
> orders에서는 오염된 날짜를 **버릴 수밖에** 없었다. 복원할 근거가 없었기 때문이다.
> 이 파일에는 **깨끗한 제3의 컬럼**이 있어서, 오염된 날짜를 근거 있게 복원할 수 있다.
> 이 문서의 핵심은 그 복원 규칙과 검증 방법이다.

## 2. 날짜 복원 — 이 파일의 핵심

### 2-1. 현황

두 날짜 컬럼 모두 같은 구조로 오염되어 있다.

| 형식 | created | resolved | 고유값 | 판정 |
|---|---|---|---|---|
| ISO 정상 (`2024-01-08T10:13:06`) | 21,000 | 21,000 | 각각 고유 | 정상 |
| 상수 `2024/31/01` | 1,860 | 1,786 | **1** | 무효 |
| 상수 `31-15-2023` | 1,787 | 1,811 | **1** | 무효 |
| 상수 `2025-12-12T28:77:10` | 1,743 | 1,727 | **1** | 무효 |
| ISO 마이크로초 (`...T15:41:44.348698`) | 1,821 | 1,853 | 각각 고유 | 무효 |
| 결측 | 1,789 | 1,823 | — | 무효 |

**무효 판정 근거**

- **상수 3종** : 각각 고유값이 1개뿐이다. 실제 일시가 아니라 시스템 대체값이다. (orders의 `2024/31/01`과 동일한 패턴)
- `31-15-2023` : **15월**이라 어떤 형식으로도 해석 불가
- `2025-12-12T28:77:10` : 날짜 부분은 멀쩡하나 **28시 77분**. 시각이 존재할 수 없다
- **ISO 마이크로초** : 시각이 전부 `15:41:44`대에 집중되고 날짜가 2027년까지 뻗는다. 적재 시점 타임스탬프다 (orders와 동일)

### 2-2. 결정적 발견 — 세 컬럼이 완벽하게 정합적이다

`resolution_time_hours` 컬럼은 완전히 깨끗하다.

| 검사 | 결과 |
|---|---|
| 결측 | **0건** |
| 값 범위 | 1 ~ 240 시간 |
| 음수 / 0 | 0건 / 0건 |

그래서 `해결일시 − 접수일시 = 처리시간` 관계가 성립하는지 검증했다.

**[산출 방법]**

```
1. 두 날짜가 모두 '진짜 정상 ISO'인 행만 고른다
   (마이크로초 형식과 시각 범위초과를 제외해야 한다.
    이걸 섞으면 일치율이 84%로 떨어져 잘못된 결론이 나온다)
2. (해결일시 − 접수일시)를 시간 단위로 계산한다
3. resolution_time_hours 와의 차이를 구한다
```

**[산출 결과]**

| 지표 | 값 |
|---|---|
| 두 날짜가 모두 정상인 티켓 | 14,687건 |
| 처리시간과의 오차 — 중앙값 | **0.000** |
| 오차 — 99분위 | **0.000** |
| 오차 — 최댓값 | **0.000** |
| 일치 건수 | **14,687 / 14,687 (100%)** |
| 해결일시 < 접수일시 | **0건** |

**오차가 0이다.** 검증 가능한 모든 건에서 세 컬럼이 정확히 맞는다.

> **주의 — 1단계 수치와 다른 이유**
> 1단계 교차검증에서는 일치율 84.5%, 논리 오류 1,323건으로 나왔다.
> 그때는 마이크로초 형식(적재시각)을 '읽히는 날짜'로 포함했기 때문이다.
> 오염된 값을 검증 대상에 넣으면 정합성이 실제보다 낮게 보인다.
> **검증할 때는 검증 대상 자체가 깨끗한지 먼저 확인해야 한다.**

### 2-3. 확정 규칙 — 한쪽이 살아 있으면 복원한다

관계식이 100% 성립하므로, 한쪽 날짜만 정상이어도 나머지를 계산할 수 있다.

```
resolved = created + resolution_time_hours
created  = resolved − resolution_time_hours
```

**[복원 가능 규모]**

| 상태 | 건수 | 처리 |
|---|---|---|
| 둘 다 정상 | 14,687 | 그대로 사용 |
| **접수만 정상 → 해결일시 복원** | **6,313** | 계산으로 채움 |
| **해결만 정상 → 접수일시 복원** | **6,313** | 계산으로 채움 |
| 둘 다 무효 | 2,687 | **NULL 유지** |

**복원 후 날짜 사용 가능 티켓 : 27,313건 (91.0%)**

복원하지 않았다면 14,687건(49.0%)만 쓸 수 있었다. **깨끗한 컬럼 하나가 사용 가능 데이터를 두 배로 늘린다.**

### 2-4. orders와 처리가 다른 이유

| | orders | support_tickets |
|---|---|---|
| 검증 가능한 제3의 컬럼 | 없음 | **있음 (처리시간)** |
| 관계식 성립률 | — | **100% (오차 0)** |
| 처리 | 전량 NULL | **복원 후 NULL 최소화** |
| 사용 가능 비율 | 70.0% | **91.0%** |

orders에서 `단가 × 수량`으로 금액을 검증하려다 상관계수 0.0008로 기각한 것과 대조된다.
**같은 발상을 시도했고, 이번에는 데이터가 뒷받침했다.**

복원된 값에는 `date_flag = '처리시간으로_복원'`을 남긴다. 계산으로 채운 값과 원본 값은 구분되어야 한다.

## 3. 컬럼별 정상 규칙

### 3-1. issue_type

| 항목 | 내용 |
|---|---|
| 허용값 | `payment` / `delay` / `refund` / `product` **4종만** |
| 현황 | **35종 혼재** |

**발견된 오염 유형 6가지**

| 유형 | 예시 | 복원 방법 |
|---|---|---|
| 앞뒤 공백 | `' refund'`, `'delay '` | 공백 제거 |
| 대문자 | `'PAYMENT'`, `'DELAY'` | 소문자 변환 |
| 접미사 부착 | `'delay_'`, `'refundx'`, `'product_'` | 끝의 `_`, `x` 제거 |
| 숫자 치환 | `'r3fund'`, `'paym3nt'`, `'d3lay'` | `3` → `e` |
| 축약형 | `'pay'`, `'pro'`, `'ref'`, `'del'` | 앞글자 매칭 |
| **문자열 뒤집기** | `'tnemyap'`, `'yaled'`, `'tcudorp'`, `'dnufer'` | **역순 배열** |

**문자열 뒤집기 — 새로운 유형**

앞선 세 파일에는 없던 패턴이다. 글자를 완전히 역순으로 배열한 형태다.

```
tnemyap  →  거꾸로 읽으면  →  payment
yaled    →                →  delay
tcudorp  →                →  product
dnufer   →                →  refund
```

**복원 규칙과 안전성**

```
값을 뒤집었을 때 정상 4종 중 하나와 정확히 일치하면 → 그 값으로 복원
일치하지 않으면 → 복원하지 않고 플래그
```

정확히 일치할 때만 복원하므로 후보가 여러 개일 위험이 없다. 우연히 다른 정상값의 역순이 되는 경우도 없다(4개 단어 모두 회문이 아니고 서로의 역순도 아니다).

**변환 순서**

```
① 앞뒤 공백 제거
② 소문자 변환
③ 끝의 _ 또는 x 제거
④ 숫자 3 → e 치환
⑤ 정상 4종에 있으면 확정
⑥ 없으면 → 역순으로 뒤집어 4종과 대조
⑦ 그래도 없으면 → 앞글자 매칭(축약형), 후보가 1개일 때만 복원
```

축약형 4종(`pay`/`pro`/`ref`/`del`) 모두 앞글자 매칭 후보가 1개씩이라 안전하다.

### 3-3. support_agent

| 항목 | 내용 |
|---|---|
| 형식 | 영문 이름, Title Case |
| 원본 고유값 | **1,556종** |
| 결측 | 0건 |

**발견된 오염 유형**

| 유형 | 건수 | 처리 |
|---|---|---|
| 앞뒤 공백 | 2,574 | 제거 |
| 전부 소문자 | 1,285 | Title Case |
| 전부 대문자 | 1,276 | Title Case |
| 접미사 `@@` | 1,300 | 제거 |
| 접미사 `--` | 1,300 | 제거 |
| 글자 중복 (`Michaael`) | 1,301 | **조건부 복원 — 아래 참고** |
| 경칭 (`Jr.`, `DDS`, `MD`) | 719 | **유지 — 오염이 아님. 아래 검증 참고** |

#### 글자 중복 복원 — 참조 컬럼 없이 검증하는 방법

CRM에서는 이메일로 이름을 검증했다. **이 파일에는 그런 참조 컬럼이 없다.**

대신 **데이터 자신을 사전으로 사용한다.**

> 같은 담당자가 여러 티켓에 등장한다(30,000건 ÷ 약 360명).
> 오염된 표기를 고쳤을 때 그 이름이 데이터 안에 이미 존재한다면,
> 그것이 정상 표기라는 증거가 된다.

**규칙**

```
① 표기 정규화 (공백 정리 · Title Case · 접미사 @@ -- 제거)
   ※ 경칭(Jr. DDS MD)은 제거하지 않는다. 이름의 일부로 취급한다.
② 정규화된 이름 전체를 '알려진 이름 사전'으로 만든다
③ 글자 중복(aa, ii, uu 등)이 있는 이름에 대해:
     중복을 줄인 형태가 사전에 존재하면  → 복원
     사전에 없으면                      → 정상 이름으로 판단, 유지
```

**[검증 결과]**

| 구분 | 종수 |
|---|---|
| 원본 고유값 | 1,556 |
| 표기 정규화 후 (공백·대소문자·`@@`·`--` 정리) | 359 |
| 글자 중복 포함 이름 | 161 |
| ├ 복원 가능 (정상형이 사전에 존재) | **159** |
| └ 유지 (사전에 없음 → 정상 이름) | **2** |
| **최종 담당자 수** | **200명** |

유지된 2종은 `Aaron Mcpherson`, `Isaac Grant`다.
최종 200명 기준으로 담당자당 평균 150건을 처리한 셈이 된다.

**이 규칙이 없었다면** `Isaac` → `Isac`, `Aaron` → `Aron`이 되어 **존재하지 않는 담당자를 만들어냈을 것이다.** CRM에서 `Bennett`, `Russell`을 지킨 것과 같은 문제를, 참조 컬럼 없이 해결했다.

#### 경칭을 제거하지 않는 이유 (검증 결과 — 초안에서 수정된 항목)

**초안의 판단**

`Jr.`, `DDS`, `MD` 719건을 제거하려 했다. 근거는 이랬다.

> 같은 사람이 `Clayton Palmer`와 `Clayton Palmer Jr.`로 나뉘어 기록되면
> 담당자가 2명으로 집계되어 실적이 쪼개진다.

**검증 — 그런 일이 실제로 있는가**

이 근거는 **확인하지 않은 가정**이었다. 실제로 세어봤다.

```
[산출 방법] 경칭을 뗀 이름(base)별로, 그 이름이 몇 가지 경칭 상태로 등장하는지 센다.
           '(없음)'도 하나의 상태로 취급한다.
           2가지 이상이면 → 같은 사람이 갈라져 기록되고 있다는 뜻이다.
```

| 이름별 경칭 상태 종류 수 | 해당 이름 수 |
|---|---|
| **1가지** | **364 (전부)** |
| 2가지 이상 | **0** |

**모든 이름이 경칭 상태가 하나씩이다.** `Michael Morgan DDS`는 항상 DDS를 달고 나오며, 경칭 없이 등장하는 경우가 **0건**이다.

→ 초안이 걱정한 "한 사람이 두 명으로 세어지는 상황"은 **이 데이터에 존재하지 않는다.**

**검증 — 제거하면 다른 사람과 충돌하는가**

동명이인 위험도 함께 확인했다.

| 검사 | 결과 |
|---|---|
| 경칭 유지 시 고유 담당자 | **359명** |
| 경칭 제거 시 고유 담당자 | **359명** |
| 경칭이 제거되는 이름 | 8종 |
| 제거 후 기존 이름과 충돌 | **0건** |

충돌은 없었다. 그러나 **359 = 359** 라는 것은 곧 **제거해도 합쳐지는 이름이 하나도 없다**는 뜻이다.

**결론**

| | 경칭 제거 | 경칭 유지 |
|---|---|---|
| 담당자 수 | 359명 | 359명 |
| 실적 통합 효과 | **없음** | — |
| 동명이인 충돌 위험 | 이 데이터에선 0, 원리적으론 존재 | 없음 |
| 원본 충실도 | 낮음 | 높음 |

**이득이 0이고 위험만 있으므로 제거하지 않는다.**

경칭은 이름의 일부로 취급하며, 담당자 사전을 만들 때도 경칭을 포함한 형태로 만든다.

> **이 수정에서 얻은 원칙**
> "이 처리가 필요하다"는 전제 자체도 검증 대상이다.
> 오염 여부는 매번 데이터로 확인했으면서, "경칭 때문에 실적이 쪼개진다"는
> 전제는 확인 없이 규칙으로 굳혔다. 확인해보니 쪼개짐은 0건이었다.
> **불필요한 처리를 하지 않기로 한 결정에도 근거가 필요하다.**

**참고** : `@@`, `--` 접미사(각 1,300건)는 여전히 제거한다. 이것은 실제 오염이며,
같은 사람이 `Michael Morgan` 과 `Michael Morgan@@` 으로 갈리는 경우가 실제로 존재한다.

### 3-4. resolution_time_hours

| 항목 | 내용 |
|---|---|
| 자료형 | 숫자 (시간) |
| 범위 | 1 ~ 240 |
| 결측 / 음수 / 0 | **모두 0건** |

**정제 불필요.** 이 파일에서 유일하게 완전히 깨끗한 컬럼이며, 날짜 복원의 기준이 된다.

깨끗한 컬럼을 명시하는 것은 중요하다. 이 컬럼 덕분에 날짜 사용 가능 비율이 49% → 91%로 올라갔다.

### 3-5. ticket_id / customer_id

| 항목 | 내용 |
|---|---|
| 형식 | UUID |
| 형식 위반 / 결측 / 중복 | 0건 |

정제 대상 아님. 4단계에서 값이 변하지 않았는지 검증용으로 사용한다.

## 4. 정제 후 산출물

`03_cleaned/support_tickets_cleaned.csv`

| 컬럼 | 설명 |
|---|---|
| ticket_id / customer_id | 변경 없음 |
| issue_type | 4종 |
| sentiment | 3종 |
| ticket_created / ticket_resolved | `YYYY-MM-DD HH:MM:SS`, 복원 불가는 빈 값 |
| resolution_time_hours | 변경 없음 |
| support_agent | 정규화된 담당자명 (경칭 포함, 200명) |
| ticket_created_raw / ticket_resolved_raw | **원본 보존** |
| support_agent_raw | **원본 보존** (정규화 전 원본 표기 그대로) |
| date_flag | `처리시간으로_복원` / `상수값` / `적재시각추정` / `시각범위초과` / `원본결측` |
| issue_flag / sentiment_flag / agent_flag | 복원 실패 시 사유 |

**원본 보존이 특히 중요한 이유**
날짜 12,626건을 **계산으로 채운다.** 원본에 없던 값을 만들어내는 것이므로, 어떤 값이 복원된 것인지 반드시 구분할 수 있어야 한다.

```sql
-- 복원된 날짜만 조회
SELECT ticket_id, ticket_created_raw, ticket_created, date_flag
FROM   support_tickets
WHERE  date_flag = '처리시간으로_복원';
```

## 5. 처리 방침 요약

| 방침 | 적용 대상 | 근거 |
|---|---|---|
| **자동 수정** | 공백·대소문자·접미사·숫자치환·축약형·역순 | 복원 결과가 유일하게 결정됨 |
| **계산 복원** | 한쪽만 정상인 날짜 12,626건 | 세 컬럼 관계식이 100% 성립 (오차 0) |
| **조건부 복원** | 담당자명 글자 중복 | 정상형이 데이터에 존재할 때만 |
| **NULL 처리** | 양쪽 날짜가 모두 무효인 2,687건 | 복원 근거 없음 |
| **행 삭제** | **없음** | 날짜가 없어도 유형·감정·처리시간은 유효 |
| **처리하지 않음** | 담당자 경칭(`Jr.`/`DDS`/`MD`) 719건 | 검증 결과 이름이 갈라지는 사례 0건 — 처리 이득 없음 |
| **원본 보존** | 날짜 2개, 담당자명 | 계산으로 채운 값과 원본을 구분해야 함 |

> **원칙** : 확신 없이 지우지 않는다. 지우는 대신 표시하고 근거를 남긴다.
> **이 파일에서 추가되는 원칙** : 오염된 컬럼을 버리기 전에, 그것을 복원할 수 있는
> **깨끗한 컬럼이 있는지 먼저 확인한다.** 단, 복원에 쓸 컬럼이 정말 깨끗한지를
> 먼저 검증해야 한다. 오염된 값을 검증 기준에 포함시키면 결론이 뒤집힌다.
