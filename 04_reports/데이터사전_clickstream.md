# 데이터 사전 & 정제 규칙서 — clickstream_500k_events

> **이 문서의 역할**
> 1단계 프로파일링 결과를 근거로 "어떤 값이 정상인가"를 확정한다.
>
> 대상 파일 : `01_raw/clickstream_500k_events.csv`
> 전체 규모 : 500,000행 × 8열
>
> **앞선 파일들과의 가장 큰 차이**
> 지금까지는 "값이 오염됐는가"를 판정했다.
> 이 파일에는 **값이 전부 정상인데 분석에 쓸 수 없는 컬럼**이 3개 있다.
> 오염 검사만으로는 절대 걸러지지 않으므로, 이 문서에는
> **컬럼 활용 가능성 판정**이라는 절이 추가된다.

## 1. 테이블 개요

사용자 행동 1건이 1행에 해당하는 이벤트 로그다.

| 컬럼 | 의미 | 활용 판정 |
|---|---|---|
| event_id | 이벤트 고유번호 (UUID) | 기본키 |
| session_id | 세션 식별자 | **사용 불가** (2절) |
| customer_id | 행동한 고객 | 사용 가능 (결측 30%) |
| event_type | 행동 유형 | 사용 (4종, 오염 없음) |
| page_url | 접속 페이지 | 사용 — **표기 오염 5종 정규화 필요** (4절) |
| device_id | 기기 식별자 | **사용 불가** (2절) |
| timestamp | 발생 시각 | 정제 후 사용 |
| ingest_run_id | 적재 배치 번호 | **사용 불가** (2절) |

## 2. 컬럼 활용 가능성 판정 — 이 파일의 핵심

### 2-1. 왜 이 판정이 필요한가

로그 데이터에는 **형식은 완벽한데 의미가 없는 컬럼**이 존재한다. 오염 검사(형식·범위·허용값)는 전부 통과하므로, 컬럼의 정의를 직접 적용해봐야 발견된다.

이 절의 세 컬럼은 모두 **결측 0건, 형식 위반 0건**이다. 그런데도 쓸 수 없다.

### 2-2. session_id — 세션 역할을 하지 못한다

**세션의 정의** : 한 사용자가 한 기기로 접속한 하나의 연속된 방문
→ 따라서 한 세션 안의 `customer_id`는 1명(또는 비로그인)이어야 하고, `device_id`도 1개여야 한다.

**[산출 방법]** `session_id`로 묶어 각 그룹의 `customer_id`·`device_id` 고유값 수를 센다.

**[산출 결과]**

| 지표 | 값 | 정상이라면 |
|---|---|---|
| 세션 수 | 8,000개 | — |
| 세션당 이벤트 수 | 62.5건 | 수 건 ~ 수십 건 |
| **세션당 고객 수 (평균)** | **43.7명** | **1명** |
| 세션당 고객 수 (최대) | 69명 | 1명 |
| **세션당 기기 수 (평균)** | **62.5개** | **1개** |

한 세션에 고객 43명과 기기 62개가 섞여 있다. 세션당 기기 수(62.5)가 세션당 이벤트 수(62.5)와 같다는 것은, **이벤트마다 기기가 다르다**는 뜻이다.

**[판정] 실제 방문 단위가 아니라 임의로 부여된 값이다. 세션 분석에 사용할 수 없다.**

**[영향] 불가능해지는 분석**

- 세션당 페이지뷰, 세션 이탈률
- 세션 내 행동 순서 (검색 → 조회 → 장바구니)

**[대안]** `customer_id` 단위로 묶어 분석한다. 단 비로그인 이벤트 30%가 제외되므로, 결과를 제시할 때 그 한계를 함께 밝힌다.

### 2-3. device_id — CRM의 device_id와 다른 것이다

이름이 같으므로 `crm_customer_devices`와 조인하고 싶어진다. 실제로 대조했다.

**[산출 결과]**

| 지표 | 값 |
|---|---|
| 클릭스트림 device_id 고유값 | 498,949개 |
| CRM 기기 목록 고유값 | 51,854개 |
| **두 목록에 함께 존재하는 건수** | **0건 / 500,000건** |
| 고유율 | 99.8% |

**단 한 건도 겹치지 않는다.** 게다가 고유율이 99.8%로 사실상 이벤트마다 다른 값이므로, 기기를 묶는 역할도 하지 못한다.

**[판정] 이름은 같지만 서로 다른 체계의 식별자다. 외래키를 걸지 않고, 조인에도 사용하지 않는다.**

> **교훈** : 컬럼 이름이 같다고 같은 의미가 아니다.
> 확인하지 않고 조인했다면 결과가 0건이 나왔을 것이다.
> 더 나쁜 경우는 일부만 우연히 겹쳐서, 틀린 결과가 그럴듯하게 나오는 것이다.

### 2-4. ingest_run_id — 전 행이 같은 값이다

| 지표 | 값 |
|---|---|
| 고유값 | **1개** |
| 값 | `920fe448-95d0-4ccb-b77b-2c7cfa389054` |

50만 행 전체가 동일하다. 적재 배치를 구분하는 메타데이터로 보인다. 오염은 아니지만 모든 행이 같으므로 어떤 구분도 만들어내지 못한다.

**[판정] 분석에 사용하지 않는다. 다만 컬럼은 남긴다** — 원본 이력 정보이며, 향후 다른 배치가 추가되면 의미를 갖게 된다.

### 2-5. 판정 요약

| 컬럼 | 결측 | 형식 위반 | 활용 판정 |
|---|---|---|---|
| session_id | 0 | 0 | **사용 불가** — 세션 역할 못 함 |
| device_id | 0 | 0 | **사용 불가** — CRM과 무관, 이벤트마다 고유 |
| ingest_run_id | 0 | 0 | **사용 불가** — 전 행 동일값 |

**8개 컬럼 중 3개가 오염 검사를 전부 통과하지만 쓸 수 없다.**
값의 정확성과 의미의 유효성은 다른 문제다.

## 3. timestamp — 형식 통일과 범위 판정

### 3-1. 현황

| 형식 | 건수 | 예시 | 판정 |
|---|---|---|---|
| `T` 구분 + 마이크로초 + 시간대 | 419,763 | `2025-09-26T16:03:31.922468+00:00` | 유효 (일부 범위 이탈) |
| **공백** 구분 + 마이크로초 + 시간대 | 19,962 | `2025-09-13 07:00:51.923083+00:00` | 유효 — 표기만 다름 |
| `T` 구분, 초 단위, 시간대 없음 | 20,102 | `2025-11-11T11:18:10` | 유효 — 표기만 다름 |
| 상수 `2024/31/01 25:61:00` | 20,011 | — | **무효** |
| 시간대만 있는 초 단위 | 2 | `2025-09-20T19:29:49+00:00` | 유효 |
| 결측 | 20,160 | — | 무효 |

**상수 `2024/31/01 25:61:00`의 무효 근거**
고유값이 1개이며, `31월` `25시 61분`으로 어떤 형식으로도 해석이 불가능하다. orders·tickets에서 본 것과 같은 시스템 대체값 패턴이다.

### 3-2. 확정 규칙 : 세 형식을 하나로 통일한다

날짜와 시각 사이 구분자가 `T`인지 공백인지, 마이크로초와 시간대가 있는지는 **표기 차이일 뿐 값은 같다.** 전부 `YYYY-MM-DD HH:MM:SS` 형태로 통일한다.

시간대는 전부 `+00:00`(UTC)이므로, 시간대 정보를 떼고 UTC 기준 시각으로 저장한다. 값이 변하지 않으므로 안전하다.

### 3-3. 유효 기간 판정 — 2025-12-02 이후를 무효로 본다

**[산출 방법]** 형식별로 날짜 범위를 따로 구한다. 형식이 다르면 생성 경로도 다를 수 있으므로, 하나로 합쳐 보면 원인을 알 수 없다.

**[산출 결과]**

| 형식 | 날짜 범위 | 2025-12-03 이후 |
|---|---|---|
| 공백 구분 + 시간대 | 2025-09-02 ~ **2025-12-02** | **0건** |
| 초 단위, 시간대 없음 | 2025-09-02 ~ **2025-12-02** | **0건** |
| `T` 구분 + 시간대 | 2025-09-02 ~ **2028-02-10** | **19,919건** |

**두 형식이 정확히 같은 3개월 구간에 갇혀 있다.** 서로 독립적인 두 표기가 동일한 경계를 보이므로, 이 구간이 실제 데이터 수집 기간이라는 증거가 된다.

**밀도 비교로 재확인**

| 구간 | 기간 | 건수 | 일평균 |
|---|---|---|---|
| 2025-09-02 ~ 2025-12-02 | 92일 | 439,908 | **4,782건** |
| 2025-12-03 ~ 2028-02-10 | 약 800일 | 19,919 | **약 24건** |

**200배 차이**다. 같은 서비스에서 발생한 로그라면 이런 격차가 날 수 없다. 게다가 초과 구간은 27개월간 월 738건씩 **거의 균등하게** 퍼져 있다. 실제 트래픽은 이렇게 고르지 않다.

**[판정] 2025-12-02 이후 19,919건은 무효로 보고 NULL 처리한다.** 사유는 `범위이탈`로 기록한다.

### 3-4. 정제 후 예상 규모

| 상태 | 건수 | 비율 |
|---|---|---|
| 유효 타임스탬프 | 439,910 | 88.0% |
| NULL — 상수값 | 20,011 | 4.0% |
| NULL — 범위 이탈 | 19,919 | 4.0% |
| NULL — 원본 결측 | 20,160 | 4.0% |

**시계열 분석 가능 88.0%.** orders(70.0%)보다 높고 tickets(91.0%)와 비슷하다.

## 4. page_url 정규화와 product_id 파생

### 4-0. 초안의 실수 — 정규화를 소홀히 해서 추출을 놓쳤다

**초안 규칙** : "page_url 값 자체는 수정하지 않는다. product_id 추출의 재료로만 사용한다."

값을 고치지 않기로 했으므로 오염 조사도 소홀히 했다. 그 결과 5단계 검증에서 아래 숫자가 나왔다.

```
page_url 고유값   3,020 → 3,019   (정규화했는데 1개만 줄었다)
```

전수 조사하니 **URL 표기 오염이 5종류**였다.

| 유형 | 예시 | 건수 |
|---|---|---|
| ① 끝 슬래시 중복 | `.../PROD-0187///` | 8,231 |
| ② 전부 대문자 | `HTTPS://SHOP.EXAMPLE.COM/PRODUCT/PROD-0412` | 8,482 |
| ③ 스킴 슬래시 과다 | `http://///shop.example.com/...` | 8,298 |
| ④ 스킴 누락 | `shop.example.com/product/...` | 8,195 |
| ⑤ 경로 축약 | `/prod////PROD-0391` | 6,213 |

**②와 ⑤ 때문에 product_id 추출에서 12,576건을 놓치고 있었다.**

| 놓친 유형 | 건수 | 원인 |
|---|---|---|
| 대문자 URL | 6,363 | 정규식이 대소문자를 구분한다 |
| 경로 축약 | 6,213 | `/product/` 만 찾았다 |

> **교훈** : 값을 수정하지 않기로 한 컬럼이라도, **그 컬럼에서 파생 컬럼을 만든다면**
> 오염 조사를 해야 한다. 오염 유형을 전수 조사하지 않으면 파생 컬럼도 함께 부정확해진다.
> `device_id`를 '사용 금지'로 판정한 뒤 형식 검사를 생략해 적재가 실패한 것과 같은 구조의 실수다.

### 4-1. 확정 규칙 — 표준 형태로 통일한다

```
표준형 : https://shop.example.com + 경로

① 앞뒤 공백 제거 후 소문자 통일
② 스킴 제거 (슬래시 개수 무관)          http://///  →  (제거)
③ 호스트 제거 후 표준 호스트로 재구성
④ 경로의 중복 슬래시를 하나로            /prod////  →  /prod/
⑤ 경로 축약 복원                        /prod/     →  /product/
⑥ 끝 슬래시 제거 (홈 '/' 는 유지)
⑦ 상품 코드만 대문자로 복원              prod-0412  →  PROD-0412
```

**⑦이 필요한 이유** : ①에서 전체를 소문자로 만들었으므로 상품 코드도 `prod-0412`가 된다. 카탈로그의 표준 형식은 `PROD-0412`이므로 되돌려야 조인이 성립한다.

**[정규화 결과]**

| 지표 | 정제 전 | 정제 후 |
|---|---|---|
| URL 고유값 | 3,020 | **504** |
| 값이 변경된 건수 | — | 47,724 |
| 스킴 오염 (과다·누락) | 16,493 | 0 |
| 대문자 표기 | 8,482 | 0 |
| 경로 축약 | 6,213 | 0 |

504종은 상품 500개 + 홈 + 검색 + 카테고리 + 장바구니다.

### 4-2. product_id 추출

정규화된 URL에서 추출한다. **정규화 전에 추출하면 12,576건을 놓친다.**

**[산출 결과]**

| 지표 | 값 |
|---|---|
| 상품 상세 페이지 URL | **368,942건** (정규화 전 356,366) |
| 추출된 상품 종류 | **500종** |
| 카탈로그(500개)에 없는 상품 | **0건** |

추출한 500종이 카탈로그와 정확히 일치한다. URL을 파싱해 만든 값이지만 마스터와 완전히 연결된다.

### 4-3. page_type 파생 — 페이지 유형 분류

URL을 정규화한 덕분에 페이지 유형을 안정적으로 분류할 수 있게 됐다. 정규화 전에는 같은 유형이 5가지 표기로 흩어져 분류가 불가능했다.

| page_type | 건수 | 비율 |
|---|---|---|
| product_detail | 368,942 | 73.8% |
| cart | 30,880 | 6.2% |
| category | 30,762 | 6.2% |
| home | 30,653 | 6.1% |
| search | 30,458 | 6.1% |
| (NULL — URL 결측) | 8,305 | 1.7% |

**이 컬럼을 만드는 이유** : SQL과 시각화 도구에서 URL 문자열을 매번 `LIKE`로 자르지 않고 바로 그룹화할 수 있다. 의도도 분명해진다.

```sql
-- 정규화·파생 전
WHERE page_url LIKE '%/product/%'
-- 정규화·파생 후
WHERE page_type = 'product_detail'
```

### 4-2. 상식 검증 — event_type과 URL의 대응

추출이 타당한지 확인하려면, 행동 유형과 URL 종류가 상식에 맞아야 한다.

| event_type | 상품 URL 있음 | 없음 |
|---|---|---|
| login | **0** | 49,813 |
| search | **0** | 74,946 |
| page_view | 285,273 | 15,141 |
| add_to_cart | 71,093 | 3,734 |

**login과 search에는 상품 URL이 하나도 없다.** 로그인 화면과 검색 결과 페이지에 특정 상품 코드가 있을 이유가 없으므로 당연한 결과다.

이런 "상식과 맞는지" 확인이 데이터 신뢰도를 판단하는 근거가 된다. 만약 login에 상품 URL이 섞여 있었다면 이벤트 유형이나 URL 중 하나가 오염됐다는 신호였을 것이다.

### 4-3. 확정 규칙

```
page_url 에서 정규식 /product/(PROD-\d{4}) 로 상품 코드를 추출해
product_id 파생 컬럼을 만든다.
추출되지 않는 URL(검색·홈·결측)은 NULL 로 둔다.
```

→ 이 컬럼으로 **상품별 조회 수와 장바구니 담기 수**를 집계할 수 있다. orders와 함께 보면 "많이 조회됐지만 안 팔린 상품"을 찾을 수 있다.

## 5. 컬럼별 정상 규칙

### 5-1. event_id

| 항목 | 내용 |
|---|---|
| 형식 | UUID |
| 결측 / 중복 / 형식 위반 | 모두 0건 |

정제 불필요. 기본키로 사용한다.

### 5-2. customer_id

| 항목 | 내용 |
|---|---|
| 형식 | UUID |
| 결측 | **150,553건 (30.1%)** |
| 고아 레코드 | 0건 |
| 등장한 고객 수 | 48,159명 (전체 48,200명) |

**결측 30%를 오염으로 보지 않는 이유**
로그인하지 않은 상태에서도 검색과 상품 조회는 가능하다. 결측은 **비로그인 상태의 행동**으로 해석하는 것이 자연스럽다.

실제로 `event_type`에 `login`이 있다는 점이 이를 뒷받침한다. 로그인이 이벤트로 기록된다는 것은 그 이전 상태(비로그인)가 존재한다는 뜻이다.

**처리** : NULL 유지. 대신 `is_logged_in` 파생 컬럼(참/거짓)을 만들어 SQL 집계를 쉽게 한다.

### 5-3. event_type

| 값 | 건수 | 비율 |
|---|---|---|
| page_view | 300,414 | 60.1% |
| search | 74,946 | 15.0% |
| add_to_cart | 74,827 | 15.0% |
| login | 49,813 | 10.0% |

**오염 없음. 4종 그대로 사용한다.**

**중요 — `purchase` 이벤트가 없다**
이 파일로는 **조회 → 장바구니**까지만 분석할 수 있다.
`장바구니 → 구매` 단계는 `orders` 테이블과 이어야 한다.
7단계 퍼널 분석을 설계할 때 이 한계를 전제로 삼는다.

### 5-4. page_url

| 항목 | 내용 |
|---|---|
| 결측 | 8,305건 (1.7%) |
| 고유값 | 3,020개 |
| 유형 | 상품 상세 356,366 / 검색 29,904 / 홈 28,633 |

**처리** : 표기 오염 5종을 표준 형태로 정규화한다 (4절 참고).
원본은 `page_url_raw` 컬럼에 보존한다.
결측 8,305건은 NULL 유지한다.

## 6. 정제 후 산출물

`03_cleaned/clickstream_cleaned.csv`

| 컬럼 | 설명 |
|---|---|
| event_id | 변경 없음 (PK) |
| session_id | 원본 유지 — **분석 사용 금지** |
| customer_id | 원본 유지 (결측 = 비로그인) |
| is_logged_in | **신규** — customer_id 존재 여부 (참/거짓) |
| event_type | 변경 없음 |
| page_url | 정규화된 URL (표준 형태로 통일) |
| page_type | **신규** — 페이지 유형 5종 |
| product_id | **신규** — page_url에서 추출 (FK → product_catalog) |
| device_id | 원본 유지 — **분석 사용 금지** |
| event_time | 정제된 타임스탬프 (`YYYY-MM-DD HH:MM:SS`, UTC) |
| timestamp_raw | **원본 보존** |
| page_url_raw | **원본 보존** |
| ingest_run_id | 원본 유지 — 분석 사용 금지 |
| time_flag | `상수값` / `범위이탈` / `원본결측` |

**`timestamp` 컬럼명을 `event_time`으로 바꾸는 이유**
`timestamp`는 PostgreSQL의 자료형 이름이다. 컬럼명으로 쓰면 쿼리에서 혼동이 생기고, 따옴표로 감싸야 하는 경우가 발생한다. 예약어와 겹치는 이름은 피하는 것이 원칙이다.

## 7. 처리 방침 요약

| 방침 | 적용 대상 | 근거 |
|---|---|---|
| **형식 통일** | timestamp 3종 표기 | 표기만 다르고 값은 동일 |
| **NULL 처리** | 상수값 20,011 / 범위이탈 19,919 | 고유값 1개 / 밀도 200배 차이 |
| **표기 정규화** | page_url 오염 5종 | 같은 페이지가 5가지 표기로 흩어져 있었음 |
| **파생 생성** | product_id, page_type, is_logged_in | 추출값 500종이 카탈로그와 완전 일치 |
| **원본 유지 + 사용 금지** | session_id, device_id, ingest_run_id | 형식은 정상이나 의미가 없음 |
| **결측 유지** | customer_id 30%, page_url 1.7% | 비로그인 행동으로 해석 |
| **원본 보존** | timestamp, page_url | 정규화·NULL 처리 건이 많아 추적 필수 |
| **행 삭제** | **없음** | 타임스탬프가 없어도 유형·상품 분석은 가능 |
| **컬럼 개명** | timestamp → event_time | DB 예약어 회피 |

> **원칙** : 확신 없이 지우지 않는다. 지우는 대신 표시하고 근거를 남긴다.
> **이 파일에서 추가되는 원칙** : 오염 검사를 통과한 컬럼도 **의미가 살아 있는지** 확인한다.
> 컬럼 이름이 같다고 같은 것이 아니며, 형식이 정상이라고 쓸 수 있는 것도 아니다.
> **쓸 수 없다는 판정도 문서에 남겨야 한다.** 그렇지 않으면 다음 사람이 같은 함정에 빠진다.
>
> **또 하나** : 값을 수정하지 않기로 한 컬럼이라도 그 컬럼에서 파생 컬럼을 만든다면
> 오염 조사를 해야 한다. page_url 오염을 조사하지 않아 product_id 12,576건을 놓쳤다.
