# 데이터 사전 & 정제 규칙서 — crm_50000_customers

> **이 문서의 역할**
> 1단계 프로파일링 결과를 근거로 "어떤 값이 정상인가"를 확정한다.
> 3단계(색출)와 4단계(정제)는 전부 이 문서를 기준으로 판정한다.
>
> 대상 파일 : `01_raw/crm_50000_customers_dirty_v3.csv`
> 전체 규모 : 50,000행 × 14열
>
> **product_catalog와의 차이**
> product_catalog는 컬럼별로 독립 처리가 가능했다.
> CRM은 **처리 순서가 결과를 바꾸고**, **다른 컬럼을 참고해야 판단이 되는** 항목이 있다.
> 그래서 이 문서에는 컬럼별 규칙 앞에 "처리 순서" 절을 먼저 둔다.

---

## 0. 이 정제본의 성격과 사용 범위 (개인정보 취급 원칙)

> **문서 내 예시 값 표기 안내**
> 이 문서의 이메일·이름 예시는 마스킹했다 (`k***.c***968@example.com`, `Denise C***`).
> 실제 도메인도 `example.com` 으로 바꿨다.
> 다만 **오염 패턴 예시(`KKeevvin`, `Tho8mas`, `Tara*`)는 원문을 유지했다.**
> 글자 반복·숫자 삽입 패턴을 보여주는 것이 설명의 핵심이라, 마스킹하면 내용이 성립하지 않는다.
>
> 원칙 : **연락처가 될 수 있는 값은 마스킹, 오염 패턴 예시는 유지.**

> **먼저 읽어야 하는 절이다.** 아래 원칙을 모르고 정제본을 사용하면 실제 피해가 발생할 수 있다.

### 0-1. 이 파일은 '분석 전용 사본'이다

| 계층 | 파일 | 성격 | 수정 |
|---|---|---|---|
| **운영 마스터** | `01_raw/crm_50000_...csv` | 진실의 원천. 고객 본인 확인·연락에 사용 | **금지** |
| **분석 사본** | `03_cleaned/crm_customers_cleaned.csv` | 집계·분석 전용 | 표준화 허용 (추적 가능해야 함) |

| 용도 | 사용 가능 여부 |
|---|---|
| 집계·통계·분석 조인 | 정제값 사용 |
| 중복 고객 판정 | 정제값 사용 |
| 고객 응대·본인 확인 | **원본값(`_raw`) 사용** |
| 메일·문자·우편 발송 | **원본값(`_raw`) 사용** |

### 0-2. 고객이 입력한 값을 우리가 바꿔도 되는가

이름·이메일·전화번호는 **고객이 직접 입력한 개인정보**다. 원칙적으로 임의 수정은 허용되지 않는다. 그러나 이번 데이터의 오염은 대부분 **고객 입력이 아니라 시스템 처리 과정에서 생긴 것**으로 판단된다. 근거는 세 가지다.

**① 사람이 입력할 수 없는 패턴이다**

```
KKeevvin      글자가 규칙적으로 중복 — 키보드로 재현하기 어렵다
Tho8mas       단어 중간에 숫자 1개가 삽입
Tara*         특수문자가 ! * @ 3종만, 항상 마지막 위치에, 균등한 비율로 등장
```

사람의 오타는 이렇게 규칙적이지 않다.

**② 이메일이 복원 결과를 뒷받침한다**

`KKeevvin`의 이메일은 `k***.c***968@example.com`이다. 입력 시점에는 `Kevin`이었고 이후 CRM 필드가 손상되었다는 정황이다. 반복 글자를 줄였을 때 이메일 일치율이 **10.0% → 78.5%** 로 상승한 것이 이를 지지한다.

**③ 정상 이름은 건드리지 않도록 규칙을 제한했다**

`Bennett`, `Russell`, `Carroll`처럼 반복쌍이 2개인 정상 성씨는 복원 대상에서 제외했다. 이메일로 검증되지 않으면 고치지 않는다.

### 0-3. 그래도 우리 판단이 개입한 항목

아래는 시스템 오염이라고 단정할 수 없는, **우리가 분석 편의를 위해 표준화한** 항목이다.

| 항목 | 처리 | 판단이 개입한 이유 |
|---|---|---|
| 대소문자 통일 | `MEAN YOUR` → `Mean Your` | 전부 대문자 입력은 고객의 입력 방식일 수 있다 |
| 이메일 소문자화 | 소문자 통일 | 이메일 로컬 파트는 규격상 대소문자 구분 가능 |
| 전화번호 형식 | 숫자만 10자리 + 내선 분리 | 고객이 입력한 표기 형태를 변경 |

→ 이 항목들은 **분석 목적의 가공**이며, 고객 입력을 정정한 것이 아니다.
→ 실제 데이터에서 `email` 컬럼은 이미 전부 소문자였으므로 변경 건수는 **0건**이었다.

### 0-4. 원본 값 보존 컬럼

개인정보 4개 컬럼은 정제 전 값을 같은 행에 함께 보관한다.

| 정제값 | 원본값 |
|---|---|
| first_name | first_name_raw |
| last_name | last_name_raw |
| email | email_raw |
| phone_number | phone_number_raw |

```sql
-- 값이 수정된 고객만 조회
SELECT customer_id, first_name_raw, first_name
FROM   crm_customers
WHERE  first_name <> first_name_raw;
```

**변경 건수 (48,200명 기준)**

| 컬럼 | 변경 건수 |
|---|---|
| first_name | 12,018 |
| last_name | 12,042 |
| email | 0 |
| phone_number | 44,276 |

**주의 사항 2가지**

- **중복 제거의 영향** : 같은 고객의 중복 행이 제거되었으므로, `_raw`에는 살아남은 행의 원본값 하나만 남는다. 제거된 행의 원본값은 `04_reports/삭제행_crm.csv`에서 확인해야 한다.
- **중복 판정에서 제외** : `_raw` 컬럼을 중복 비교에 포함시키면 안 된다. `Peck`과 `PECK`은 정제 후 같아지지만 `_raw`에는 원래 표기가 남아 있어, 비교에 넣으면 중복 제거가 무력화된다.

### 0-5. 다른 데이터에 재사용할 때의 주의

이 데이터에서는 안전했지만, **일반적인 고객 데이터에는 그대로 적용하면 안 되는 규칙**이 있다.

이름 컬럼의 비영문자를 전수 조사한 결과, 이 데이터에는 `! * @` 와 숫자만 존재했고 아포스트로피·하이픈·비라틴 문자는 **0건**이었다. 그래서 "영문자 외 제거 + Title Case" 규칙이 실제 이름을 훼손하지 않았다.

그러나 실제 데이터라면 다음과 같이 파괴된다.

| 원본 | 규칙 적용 후 | 판정 |
|---|---|---|
| `O'Brien` | `Obrien` | 훼손 |
| `McDonald` | `Mcdonald` | 훼손 |
| `van der Berg` | `Van Der Berg` | 훼손 |
| `김민수` | (빈 값) | 완전 손실 |

→ 재사용 시에는 허용 문자 집합에 아포스트로피·하이픈·유니코드 문자를 포함시키고, `Mc`/`Mac`/`van`/`de` 등의 예외 처리를 먼저 추가해야 한다.

## 1. 테이블 개요

고객 마스터 테이블. 고객 1명이 1행에 해당해야 한다.
`orders`, `support_tickets`, `clickstream`이 모두 `customer_id`로 이 테이블을 참조하는 **프로젝트의 중심 테이블**이다.

| 컬럼 | 의미 | 역할 |
|---|---|---|
| customer_id | 고객 고유번호 (UUID) | 기본키(PK) — **중복 1,734개 존재** |
| first_name / last_name | 이름 / 성 | 속성 |
| email | 이메일 | 속성 + 이름 검증 참고자료 |
| phone_number | 전화번호 | 속성 |
| gender | 성별 | 범주형 |
| dob | 생년월일 | 날짜 |
| signup_date | 가입일 | 날짜 |
| address / city / state / country | 주소 정보 | 속성 (**신뢰도 낮음**) |
| device_id(s) | 보유 기기 ID | **다중값 — 구조 문제** |
| source | 유입 경로 | 범주형 |

## 2. 처리 순서 (가장 중요)

### 2-1. 왜 순서가 중요한가

`customer_id`가 같은데 다른 값이 미묘하게 다른 행이 있다.

```
30391  00682ed4...  Melissa  Peck   ← 나머지 12개 컬럼 전부 동일
38030  00682ed4...  Melissa  PECK   ← 성씨 대소문자만 다름
```

컴퓨터는 `Peck`과 `PECK`을 다른 값으로 본다. 따라서 **중복 제거를 먼저 하면 이 행은 살아남고, 표기 통일을 먼저 하면 제거된다.**

실제로 검증한 결과는 이렇다.

| 처리 순서 | 발견되는 완전 중복 |
|---|---|
| 표기 통일 **전** 중복 제거 | 1,021건 |
| 표기 통일 **후** 중복 제거 | **1,789건** |

**표기를 먼저 통일하면 768건을 추가로 발견한다.** 순서를 잘못 잡으면 중복 고객이 768명 남는다.

### 2-2. 확정 순서

```
① 컬럼별 값 정제        (공백·대소문자·특수문자·오타)
② 컬럼 간 교차 검증      (이메일로 이름 검증, 날짜 조합 검증)
③ 완전 중복 행 제거      ← ①이 끝난 뒤여야 효과가 있다
④ 잔여 기본키 충돌 처리   (①③으로도 안 지워진 것)
⑤ device_id 분리 준비    (6단계 별도 테이블용)
```

## 3. 컬럼별 정상 규칙

### 3-1. customer_id

| 항목 | 내용 |
|---|---|
| 형식 | UUID (8-4-4-4-12 자리 16진수) |
| 형식 위반 | **0건 — 형식은 정상** |
| 결측 | 0건 |
| **중복** | **1,734개 ID / 3,534행** ← 기본키 위반 |

**처리 방침**

| 단계 | 처리 | 예상 결과 |
|---|---|---|
| ①③ 표기 통일 후 중복 제거 | 완전히 같아진 행 삭제 | 3,534행 → 1,745행 |
| ④ 잔여 충돌 | 값이 여전히 다른 행 | 약 11~18개 ID |

**잔여 충돌의 실제 내용** (검증 결과)

```
bf4e3ff5...  last_name : 'Russel'  vs  'Rusel'
75d93908...  last_name : 'Mcgee'   vs  'Mcge'
a91b1627...  first_name: 'Alyssa'  vs  'Alysa'
```

전부 이름 철자가 한 글자 다른 경우다. 동일 인물이 확실하므로 **한 행만 남긴다.**
남길 행을 고르는 기준은 아래 3-2의 이름 복원 규칙과 연동한다(이메일과 일치하는 쪽을 남긴다).

---

### 3-2. first_name / last_name

| 항목 | 내용 |
|---|---|
| 형식 | 영문자만, 첫 글자만 대문자 (Title Case) |
| 결측 | 0건 |

**발견된 오염 (first_name / last_name)**

| 유형 | 건수 | 예시 |
|---|---|---|
| 앞뒤 공백 | 3,124 / 3,134 | `' Cantu'` |
| 전부 대문자 | 1,608 / 1,626 | `'JAY'` |
| 전부 소문자 | 1,527 / 1,539 | `'day'` |
| 숫자 삽입 | 1,543 / 1,584 | `'Tho8mas'`, `'Ha0rt'` |
| 특수문자 부착 | 1,561 / 1,502 | `'Tara*'`, `'Thompson*'` |
| 글자 반복 오타 | 1,768 / 2,258 | `'KKeevvin'`, `'JJoonnes'` |

**공백·대소문자·숫자·특수문자는 자동 수정.** 사람 이름에 숫자나 `*`, `!`, `@`가 들어갈 이유가 없으므로 제거해도 안전하다. (주소는 다르다 — 3-7 참고)

#### 글자 반복 오타 복원 — 여기가 이 파일에서 가장 까다로운 부분

`'KKeevvin'`을 `'Kevin'`으로 만들려면 반복된 글자를 하나로 줄이면 된다. 문제는 **`'Aaron'`, `'Lee'`, `'Brooks'`처럼 반복이 정상인 이름도 있다**는 것이다.

세 가지 방법을 실제 데이터로 검증했다. 검증 기준은 이메일이다. 이메일이 `firstname.lastname숫자@도메인` 형식이므로 정답 대조가 가능하다.

| 방법 | 이메일과 일치율 |
|---|---|
| 아무것도 안 함 | 90.0% |
| **반복을 무조건 하나로 줄이기** | **75.9% (악화)** |
| 반복쌍이 2개 이상일 때만 줄이기 | 92.5% |
| 이메일과 대조해서 줄이기 | 92.8% |

**무조건 줄이면 오히려 나빠진다.** 정상 이름을 망가뜨리기 때문이다. 반복쌍이 1개인 이름 8,452건에 적용해봤더니 일치율이 **93.1% → 0.0%** 로 붕괴했다. (`Aaron` → `Aron`, `Lee` → `Le`)

반대로 반복쌍이 2개 이상인 1,768건에 적용하면 일치율이 **10.0% → 78.5%** 로 올라간다.

**확정 규칙 (이메일 우선, 추정은 최후 수단)**

```
① 숫자·특수문자 제거, 앞뒤 공백 제거
② 이메일을 쓸 수 있는가? (이메일 존재 + shared~ 아님)
   ├─ 예 → 현재 이름이 이메일과 일치하면          → 그대로 유지
   │        반복을 줄였을 때 이메일과 일치하면      → 줄인 값 채택 [이메일로복원]
   │        둘 다 아니면                          → 원본 유지 + 플래그 [이메일불일치_보류]
   └─ 아니오 → 반복쌍이 2개 이상이면              → 줄인 값 채택 [추정복원]
                그 외                            → 그대로 유지
```

**적용 결과 (first_name 기준)**

| 판정 | 건수 |
|---|---|
| 이메일과 이미 일치 | 42,686 |
| 이메일로 복원 | 1,316 |
| 이메일 불일치 → 보류+플래그 | 3,408 |
| 이메일 없어 추정 복원 | 92 |
| 이메일 없음, 반복 정상 → 유지 | 2,498 |

**`이메일불일치_보류` 3,408건을 덮어쓰지 않는 이유**
이 안에는 이메일 자체가 오염된 건이 섞여 있다.

```
Denise C***  ↔  d***.s***863@example.com    ← 완전히 다른 사람
Holly H***   ↔  d***.s***649@example.com  ← 완전히 다른 사람
```

이메일을 무조건 신뢰하면 `Denise C***`가 `D*** S***`로 바뀐다. **이름과 이메일 중 무엇이 오염됐는지 알 수 없으므로 둘 다 원본을 유지하고 플래그만 남긴다.**

### 3-3. email

| 항목 | 내용 |
|---|---|
| 형식 | `로컬@도메인.tld` — **형식 위반 0건** |

공용 이메일은 `email_flag = '공용이메일'`로 표시한다. 이름 검증에 쓸 수 없기 때문에 표시가 필요하다.

### 3-4. phone_number

| 항목 | 내용 |

| 형식 | **7종이 혼재 — 표준화 대상** |

| 내선번호 포함 (`449.977.1729x282`) | 29,966 |
| 10자리 숫자 (`1974876994`) | 4,060 |
| `xxx.xxx.xxxx` | 4,023 |
| `xxx-xxx-xxxx` | 4,016 |
| `(xxx)xxx-xxxx` | 3,913 |
| `+1-` 국가코드 | 2,056 |
| `001-` 국가코드 | 1,966 |

**확정 규칙 — 컬럼을 2개로 분리한다**

```
원본: 449.977.1729x282
  → phone_number : 4499771729   (숫자만, 10자리)
  → phone_ext    : 282          (내선번호)
```

**분리하는 이유**
`x` 뒤의 내선번호는 전화번호 본체가 아니다. 합쳐두면 숫자 길이가 10~18자리로 들쭉날쭉해서 `LENGTH()` 검증이나 중복 확인이 불가능하다. 분리하면 본체는 전부 10자리로 통일되고, 내선 정보도 잃지 않는다.

`+1-`, `001-` 국가코드는 미국 국가번호이므로 제거하고 10자리만 남긴다.
정제 후 10자리가 아닌 값은 `phone_flag`에 표시한다.

### 3-5. gender / source

| 컬럼 | 값 | 판정 |
|---|---|---|
| gender | `F` 23,333 / `M` 22,880 / `O` 3,787 | **정상 — 정제 불필요** |
| source | `referral` 16,768 / `app` 16,692 / `web` 16,540 | **정상 — 정제 불필요** |

깨끗한 컬럼이 있다는 것도 리포트에 명시해야 한다. "전 컬럼이 오염"이라는 인상은 부정확하다.

### 3-6. dob / signup_date

| 항목 | dob | signup_date |
|---|---|---|
| 형식 (`YYYY-MM-DD`) 위반 | **0건** | **0건** |
| 값 범위 | 1954-12-20 ~ 2007-12-07 | 2013-12-02 ~ 2025-12-01 |
| 결측 | 0건 | 0건 |

**컬럼 하나만 보면 완벽하다.** 문제는 두 컬럼의 조합에서 나온다.

| 검사 | 결과 |
|---|---|
| 가입일이 생년월일보다 앞선 행 | 0건 |
| 가입 시점 나이 최소 | **6.0세** |
| 가입 시점 14세 미만 | **2,415건** |

**처리 방침 : 값 수정 없이 `age_flag`로 표시**

날짜 두 개 중 **무엇이 틀렸는지 알 수 없다.** 생년월일이 잘못됐을 수도, 가입일이 잘못됐을 수도 있다. 어느 쪽을 고쳐도 근거 없는 추측이다.

또한 6세 가입이 실제로 가능하기도 하다. 부모가 자녀 계정을 만드는 서비스라면 정상 데이터다.

→ 값은 그대로 두고 `age_flag = '가입시_14세미만'`으로 표시한다.
→ 계산 편의를 위해 `age_at_signup` (가입 시점 나이) 컬럼을 파생 생성한다. SQL 분석에서 연령대별 집계에 바로 쓸 수 있다.

### 3-7. address / city / state / country

**주소 관련 컬럼은 신뢰도가 낮다.**

| 검사 | 결과 |
|---|---|
| state 고유값 | 50종 (전부 미국 주 이름) |
| country 고유값 | 243종 |
| country가 미국인 행 | **646건 (1.3%)** |

`Oregon`주에 사는 `Micronesia` 거주자, `Delaware`주에 사는 `Portugal` 거주자가 대량으로 존재한다. **state와 country가 서로 모순되므로 지역 정보 자체를 신뢰할 수 없다.**

**처리 방침**

| 컬럼 | 처리 |
|---|---|
| address | 앞뒤 공백 제거 + Title Case (전부 대문자 597건 대응). **숫자는 유지** — 번지수이므로 정상 |
| city | 앞뒤 공백 제거 + Title Case |
| state | 앞뒤 공백 제거 + Title Case, 값 자체는 유지 |
| country | 앞뒤 공백 제거 + Title Case, 값 자체는 유지 |
| 전체 | 테이블 수준 주석에 **"지역 정보 신뢰도 낮음 — 분석 축으로 사용 비권장"** 기록 |

**이름과 주소를 다르게 처리하는 이유**
`'Tho8mas'`의 숫자는 오염이지만 `'107 Joseph Station'`의 숫자는 번지수다.
같은 "숫자 포함" 패턴이라도 컬럼의 의미에 따라 판정이 정반대가 된다.
1단계 리포트에서 address의 "숫자포함"이 50,000건으로 나온 것은 오탐이다.

### 3-8. device_id(s)

| 항목 | 내용 |
|---|---|
| 형식 | UUID, 세미콜론(`;`)으로 구분 — **형식 위반 0건** |
| 보유 개수 | 1개 48,748명 / 2~6개 1,252명 |
| 총 등록 건수 | 53,796건 |
| 고유 기기 ID | 51,854개 (1,942건은 여러 고객이 공유) |

**이것은 오염이 아니라 구조 문제다.**
관계형 데이터베이스 설계 원칙(제1정규형)은 "한 칸에는 값이 하나만" 요구한다.
현재 상태로는 SQL에서 `기기 3개 이상 보유 고객`을 조회하려면 문자열을 세어야 해서 비효율적이고, 기기 단위 조인이 불가능하다.

**처리 방침 — 테이블 분리**

```
customers (50,000행 → 중복 제거 후)
  customer_id (PK) | first_name | ... | device_count

customer_devices (53,796행)
  customer_id (FK) | device_id
```

정제본은 CSV 2개로 산출한다.
`device_count` 파생 컬럼을 customers에 남겨두면 간단한 집계는 조인 없이 가능하다.

## 5. 처리 방침 요약

| 방침 | 적용 대상 | 근거 |
|---|---|---|
| **자동 수정** | 이름/주소 공백·대소문자, 이름의 숫자·특수문자, 전화번호 형식 | 정답이 명확 |
| **조건부 복원** | 이름 글자 반복 오타 | 이메일과 대조 성공 시에만 |
| **행 삭제** | 표기 통일 후 완전 중복 행 (약 1,789건) | 동일 고객 중복 등록 |
| **유지 + 플래그** | 이메일-이름 불일치, 14세 미만 가입, 공용 이메일 | 무엇이 틀렸는지 알 수 없음 |
| **테이블 분리** | device_id(s) | 제1정규형 준수 |
| **원본 유지 + 주석** | state / country 모순 | 값을 고칠 근거가 없음 |

> **원칙 (product_catalog와 동일)** : 확신 없이 지우지 않는다. 지우는 대신 표시하고 근거를 남긴다.
> **CRM에서 추가된 원칙** : 다른 컬럼을 근거로 값을 고칠 때는, 그 근거 컬럼이 신뢰할 수 있는지 먼저 검증한다.
