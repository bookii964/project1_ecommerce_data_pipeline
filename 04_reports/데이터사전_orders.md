# 데이터 사전 & 정제 규칙서 — orders_300k

> **이 문서의 역할**
> 1단계 프로파일링 결과를 근거로 "어떤 값이 정상인가"를 확정한다.
> 3단계(색출)와 4단계(정제)는 전부 이 문서를 기준으로 판정한다.
>
> 대상 파일 : `01_raw/orders_300k_dirty.csv`
> 전체 규모 : 300,000행 × 8열
>
> **앞선 두 파일과의 차이**
> product_catalog와 crm은 **마스터 데이터**였다. 상품 목록, 고객 명부처럼 대상 자체를 정의한다.
> orders는 **거래 데이터**다. 마스터를 참조해 "누가 무엇을 샀는가"를 기록한다.
> 그래서 이 문서에는 **참조 정합성**과 **집계 왜곡 위험**이라는 관점이 추가된다.

## 1. 테이블 개요

주문 1건이 1행에 해당한다.

| 컬럼 | 의미 | 역할 |
|---|---|---|
| order_id | 주문 고유번호 (UUID) | 기본키(PK) — 중복 0건 |
| customer_id | 주문한 고객 | 외래키 → `crm_customers` |
| product_id | 주문한 상품 | 외래키 → `product_catalog` |
| order_amount | 주문 금액 | 수치 분석의 핵심 |
| order_date | 주문 일자 | 시계열 분석의 핵심 |
| payment_method | 결제 수단 | 범주형 |
| status | 주문 상태 | 범주형 |
| quantity | 주문 수량 | 수치 |

### 참조 정합성 (1단계 검사 결과)

| 검사 | 결과 |
|---|---|
| 고아 주문 (없는 고객 참조) | **0건** |
| 고아 주문 (없는 상품 참조) | **0건** |
| order_id 중복 | **0건** |
| 완전 중복 행 | **0건** |

→ 구조적으로는 건강한 테이블이다. 문제는 **개별 컬럼의 값**에 있다.

## 2. order_date — 이 파일에서 가장 중요한 판단

### 2-1. 현황

| 형식 | 건수 | 고유값 수 | 예시 |
|---|---|---|---|
| `YYYY-MM-DD` (표준) | 210,000 (70.0%) | 730 | `2025-07-29` |
| `YYYY/MM/DD` | 18,110 (6.0%) | **1** | `2024/31/01` |
| `DD-MM-YYYY` | 18,050 (6.0%) | **1** | `31-12-2023` |
| `YYYY/MM/DD HH:MM` | 17,952 (6.0%) | **1** | `2025/01/10 12:00` |
| `ISO8601` | 17,974 (6.0%) | 17,974 | `2026-12-20T15:18:00.441995` |
| 결측 | 17,914 (6.0%) | — | |

### 2-2. 확정 규칙 : 비표준 형식 4종을 전부 NULL 처리한다

형식 변환으로 되살리지 않는다. 근거는 아래와 같다.

#### 근거 ① 고유값이 1개면 날짜가 아니라 상수다

`2024/31/01` 18,110건이 **전부 똑같은 값**이다. 다양한 날짜가 다른 형식으로 저장된 것이 아니다. 시스템이 값을 채우지 못했을 때 넣은 대체값으로 보인다. (product_catalog의 `price = -100`이 26건 전부 동일했던 것과 같은 패턴)

#### 근거 ② 변환하면 집계가 파괴된다

**[산출 방법]**

```
1단계. 기준선 만들기
   표준 형식(YYYY-MM-DD) 주문만 골라낸다              → 210,000건
   주문이 실제로 존재한 날의 수를 센다                 → 730일
   하루 평균 = 210,000 ÷ 730                        → 287.7건

   ※ 기간 전체 일수가 아니라 '주문이 있었던 날'로 나눈다.
     주문이 0건인 날이 있으면 평균이 낮아져 비교가 불공정해진다.

2단계. 변동 폭 확인 (평균만으로는 판단할 수 없다)
   일별 주문 건수의 최소/중앙값/최대를 구한다
   → 최소 244건 / 중앙값 287건 / 최대 343건
   → 평상시 하루 주문은 343건을 넘은 적이 없다

3단계. 변환 시뮬레이션
   상수값을 형식만 보고 날짜로 변환했다고 가정하고,
   그날의 총 건수 = 원래 있던 정상 주문 + 변환되어 들어온 건수
   이를 하루 평균과 비교한다
```

**[산출 결과]**

| 오염값 | 변환 결과 | 해당일 기존 주문 | 추가되는 건수 | 변환 후 합계 | 평균 대비 |
|---|---|---|---|---|---|
| `2024/31/01` | 2024-01-31 | 285 | 18,110 | 18,395 | **63.9배** |
| `31-12-2023` | 2023-12-31 | 276 | 18,050 | 18,326 | **63.7배** |
| `2025/01/10 12:00` | 2025-01-10 | 302 | 17,952 | 18,254 | **63.5배** |

**[해석]**

하루 평균 287.7건, **실제 최대치가 343건**인 데이터에서 특정 3일만 18,000건대로 치솟는다. 실제 최대치의 53배다.

이 상태로 월별 매출을 집계하면 2023년 12월, 2024년 1월, 2025년 1월이 비정상적인 성수기로 보인다. **월별 추이·계절성 분석·전년 대비 성장률이 전부 무의미해진다.**

형식이 복원 가능하다는 것과 값이 진실이라는 것은 다른 문제다.

> 재현 : `python scripts/10_evidence_orders_date.py`
> 결과 : `04_reports/근거_일별주문건수_시뮬레이션.csv`

**[산출 방법]**

```
① 시각(HH:MM)별로 건수를 센다
   실제 주문이라면 하루 종일 고르게 퍼져야 한다.
```

**[해석]**

주문 17,974건이 **2분 안에** 몰릴 수 없고, 아직 오지 않은 날짜에 주문이 있을 수도 없다.
**데이터 적재 시점에 생성된 타임스탬프**로 판단된다.

#### 근거 ④ 오염이 무작위로 발생했다

**[왜 이걸 확인해야 하는가]**

날짜 9만 건을 버리고 나머지 21만 건으로 분석할 예정이다.
만약 **특정 성격의 주문만 날짜가 깨졌다면**(예: 환불 건만), 남은 21만 건은 편향된 표본이 되어 분석 결과 자체가 틀린다. 환불률이 실제보다 낮게 나오는 식이다.

반대로 오염이 무작위라면, 남은 데이터는 전체를 대표할 수 있다.
**즉 이 검증을 통과해야만 "버려도 된다"는 결론이 성립한다.**

**[산출 방법 — 2가지를 함께 본다]**

```
① 구성비 비교
   날짜가 정상인 그룹과 오염된 그룹으로 나눈 뒤,
   각 그룹의 status 구성비(success/refunded/failed)를 나란히 놓고 비교한다.
   ※ status는 대소문자·축약형이 섞여 있으므로 임시로 정규화한 뒤 비교한다.

② 카이제곱 검정 (chi-square test)
   눈으로 "비슷해 보인다"고 판단하면 주관이 개입한다.
   두 그룹의 구성비가 '같다고 봐도 되는가'를 통계적으로 판정한다.

   판정 기준 : p-value > 0.05  →  차이가 우연 범위 안 (같다고 본다)
              p-value ≤ 0.05  →  우연으로 보기 어려운 차이가 있다

   여기서는 p-value가 크게 나와야 무작위 오염이라는 결론이 성립한다.
   (보통은 p-value가 작기를 기대하지만, 이 검증은 반대다)
```

**[산출 결과 ① — 구성비 비교]**

| 구분 | success | refunded | failed | 건수 |
|---|---|---|---|---|
| 정상 날짜 (기준) | 73.7% | 14.3% | 12.0% | 210,000 |
| 오염 날짜 전체 | 73.8% | 14.2% | 12.0% | 90,000 |
| ├ 상수값 3종 | 73.9% | 14.1% | 12.0% | 54,112 |
| ├ ISO 형식 | 73.7% | 14.1% | 12.1% | 17,974 |
| └ 원본 결측 | 73.6% | 14.5% | 12.0% | 17,914 |

오염 유형별로 나눠서 봐도 전부 기준선과 일치한다.

**[산출 결과 ② — 카이제곱 검정]**

교차표 (실제 관측값)

| | failed | refunded | success |
|---|---|---|---|
| 날짜 정상 | 25,097 | 30,059 | 154,844 |
| 날짜 오염 | 10,796 | 12,768 | 66,436 |

| 지표 | 값 |
|---|---|
| 카이제곱 통계량 | 0.8763 |
| 자유도 | 2 |
| **p-value** | **0.6452** |

`p-value 0.6452 > 0.05` → 두 그룹의 상태 구성비에 **통계적으로 의미 있는 차이가 없다.**

**[교차 검증 — 변수를 하나만 보고 판단하지 않는다]**

status 하나로 판단하면 우연히 일치했을 가능성이 남는다. 결제수단(`payment_method`)으로도 같은 검정을 했다.

| 지표 | 값 |
|---|---|
| 카이제곱 통계량 | 4.8240 |
| p-value | 0.1851 |

역시 `> 0.05`로 차이가 없다.

**[결론]**

날짜 오염은 특정 상태나 결제수단의 주문에 몰려 있지 않고 **무작위로 발생했다.**
따라서 정상 날짜 21만 건만으로 분석해도 표본이 한쪽으로 치우치지 않는다.

> 재현 : `python scripts/10_evidence_orders_date.py`
> 결과 : `04_reports/근거_orders_날짜처리.txt`

### 2-3. 이 결정의 대가

날짜를 쓸 수 있는 주문이 300,000건 → **210,000건(70%)** 으로 줄어든다.

그럼에도 이 선택을 하는 이유는, **틀린 날짜 30%가 섞인 100%보다 믿을 수 있는 70%가 낫기** 때문이다. 날짜가 없는 주문도 금액·상품·고객 정보는 온전하므로, 시계열이 아닌 분석(상품별 매출, 고객별 구매액)에는 그대로 사용할 수 있다.

→ `date_flag` 컬럼에 사유를 기록한다 (`상수값`, `적재시각추정`, `원본결측`).

## 3. 컬럼별 정상 규칙

### 3-1. order_id / customer_id / product_id

|---|---|
| 형식 | UUID (order_id, customer_id) / `PROD-####` (product_id) |

→ 정제 대상 아님. 4단계에서 값이 변하지 않았는지 검증용으로 사용한다.

---

### 3-2. order_amount

| 항목 | 내용 |
|---|---|
| 자료형 | 숫자 (소수점 2자리) |
| 허용 범위 | 0보다 큰 값 |

| 오염 유형 | 건수 | 처리 |
|---|---|---|
| 앞뒤 공백 (`' 40344.97'`) | 25,592 | 자동 수정 (표준화) |
| 소수점 자릿수 불일치 | 25,072 | 자동 수정 (표준화) |
| 결측 | 12,830 | NULL 유지 |
| 상수값 `'0'` | 12,988 | **NULL 처리** |
| 상수값 `'1,200'` | 12,897 | **NULL 처리** |
| 상수값 `'-50'` | 12,810 | **NULL 처리** |

#### 금액에도 상수형 오염이 있다 (3단계에서 발견)

1단계에서는 "음수 12,810건 / 0원 12,988건"으로만 셌다. 3단계에서 값 단위로 다시 세어보니 **세 값이 각각 하나의 값으로만 반복**되고 있었다.

**[산출 방법]** 금액을 값별로 세고, 정상값의 최대 반복 횟수와 비교한다.

| 값 | 반복 횟수 |
|---|---|
| `'0'` | 12,988 |
| `'1,200'` | 12,897 |
| `'-50'` | 12,810 |
| (정상 양수값 중 최다 반복) | **3** |

정상 금액은 243,046종이 흩어져 있고 같은 값이 3번 넘게 나오지 않는다. 반면 위 세 값만 1만 건 넘게 반복된다. → **시스템 대체값(sentinel)** 으로 판단한다.

**`'1,200'`을 형식 변환하지 않는 이유**

이 값은 데이터 전체에서 **유일하게 천단위 쉼표를 쓴다.** 형식만 보면 `1200.00`으로 변환할 수 있지만, 변환하면 "1,200원 주문이 12,897건 있었다"는 **없는 사실**을 만들어낸다. `order_date`의 상수값을 변환하지 않는 것과 같은 이유다.

> 참고 : 1,200 근처(1,190~1,210)의 정상 주문은 별도로 13,001건 존재한다.
> 즉 1,200원이라는 금액 자체가 불가능한 게 아니라, **동일 값의 비정상적 반복**이 문제다.

**음수를 환불로 해석하지 않는 이유 (검증 결과)**

음수 12,810건이 **전부 `-50`이라는 동일한 값**이라는 점 자체가 이미 환불이 아님을 시사한다. 환불이라면 원래 주문 금액에 따라 값이 달라야 한다. 통계적으로도 확인했다.

회계 데이터에서 음수 금액은 환불을 의미하는 경우가 있다. 실제로 그런지 `status`와 교차 검증했다.

| 구분 | success | refunded | failed |
|---|---|---|---|
| 전체 평균 | 73.8% | 14.3% | 12.0% |
| 금액이 음수인 행 | 73.7% | 14.6% | 11.7% |

**환불 건에 음수가 몰려 있지 않다.** 전체 분포와 사실상 동일하므로, 음수는 환불 표기가 아니라 무작위 오염이다.
→ 유지하면 매출 합계가 과소 집계되므로 NULL 처리한다. 사유는 `amount_flag`에 기록한다.

### 3-3. quantity

| 항목 | 내용 |
|---|---|
| 자료형 | 정수 |
| 정상 범위 | 1 ~ 5 |

| 값 | 건수 | 처리 | 근거 |
|---|---|---|---|
| `1`~`5` | 225,000 | 유지 | 정상 |
| `five` | 15,097 | **→ 5로 변환** | 영어 수사, 해석이 유일함 |
| `2.0` | 15,036 | **→ 2로 변환** | 소수 표기, 값은 동일 |
| `-3` | 14,939 | **NULL 처리** | 수량은 음수일 수 없음 |
| `0` | 14,878 | **NULL 처리** | 0개 주문은 성립하지 않음 |
| `' '` (공백) | 15,050 | **NULL 처리** | 실질 결측 |

**`-3`을 절댓값 3으로 바꾸지 않는 이유**
음수가 환불 수량일 가능성을 `status`와 교차 검증했다. `-3`인 행의 상태 분포(success 73.5% / refunded 14.4%)가 전체 평균과 동일해서, **환불과 무관한 무작위 오염**으로 확인됐다.
부호만 뒤집으면 근거 없이 주문 수량 44,817개를 만들어내는 것이 된다.

**`five` → `5` 변환은 안전한 이유**
해석이 하나뿐이고, 정상 범위(1~5) 안에 들어간다. `KKeevvin` → `Kevin`처럼 원래 값이 명확한 복원에 해당한다.

### 3-4. payment_method

| 항목 | 내용 |
|---|---|
| 허용값 | `card` / `cash` / `upi` / `wallet` **4종만** |
| 현황 | **11종 혼재** |

| 원본 값 | 건수 | 변환 | 오염 유형 |
|---|---|---|---|
| `cash` | 56,446 | (유지) | 정상 |
| `wallet` | 56,364 | (유지) | 정상 |
| `card` | 56,174 | (유지) | 정상 |
| `upi` | 56,016 | (유지) | 정상 |
| `CRAD` | 10,850 | → card | 전치 오타(글자 순서 뒤바뀜) |
| `' upi'` | 10,822 | → upi | 앞 공백 |
| `'UPI '` | 10,731 | → upi | 대문자 + 뒤 공백 |
| `WALLET` | 10,696 | → wallet | 대문자 |
| `c@rd` | 10,684 | → card | 특수문자 치환 |
| `wall-et` | 10,631 | → wallet | 하이픈 삽입 |
| `cd` | 10,586 | → card | 축약(중간 글자 생략) |

**변환 순서**

```
① 앞뒤 공백 제거
② 소문자 변환
③ 특수문자(@ - _) 제거 및 치환   c@rd → crd, wall-et → wallet
④ 매핑 사전으로 최종 확정        crad/crd/cd → card
```

**축약형 매핑 규칙 — 앞글자 매칭에서 부분열 매칭으로 수정**

처음에는 product_catalog에서 쓴 방식(`clo` → `clothing`)대로 **앞글자 매칭**을 쓰려 했다. 그런데 3단계에서 실제로 돌려보니 `cd`가 복원되지 않았다.

```
'cd'.startswith 로 card 를 찾으려 하면 실패한다.
'card'는 'ca'로 시작하므로 'cd'로는 매칭되지 않는다.
```

값을 다시 보니 오염 패턴이 **앞글자 축약이 아니라 중간 글자 생략**이었다.

```
card  →  crd  (모음 a 생략)  →  cd  (r까지 생략)
```

그래서 **부분열(subsequence) 매칭**으로 규칙을 바꿨다. 글자 순서를 유지한 채 일부만 남긴 형태인지 확인하는 방식이다.

| 축약값 | card 안에서의 위치 | 부분열 후보 | 판정 |
|---|---|---|---|
| `cd` | `c__d` | card | 유일 → 복원 |
| `crd` | `c_rd` | card | 유일 → 복원 |
| `crad` | 순서 불일치 | 없음 | 부분열 아님 → 전치오타 규칙으로 처리 |

`cash`에는 `d`가 없고 `upi`·`wallet`에는 `c`가 없으므로 후보가 `card` 하나뿐이다. **후보가 2개 이상이면 자동 변환을 포기하고 플래그 처리한다.**

`crad`는 부분열이 아니지만 **글자 구성이 `card`와 동일**하다(전치 오타). 별도 규칙으로 처리한다.

> 이 수정은 "규칙을 문서로 먼저 정하고 코드로 검증하는" 절차가 작동한 사례다.
> 3단계에서 `복원불가_미확인값 21,270건`이 나온 것을 보고 규칙의 오류를 발견했다.
> 규칙을 검증 없이 4단계로 넘겼다면 결제수단 21,270건이 그대로 유실됐을 것이다.

## 4. 시도했다가 기각한 검증 방법

정제 규칙을 정할 때 검토했으나 데이터가 뒷받침하지 않아 채택하지 않은 방법이다. 기각 사실도 기록해두어야 판단 과정이 남는다.

### 4-1. 주문 금액을 `단가 × 수량`으로 검증하기

`product_catalog`의 단가와 대조하면 금액 오류를 잡을 수 있을 것으로 보였다. 실제로 계산했다.

| 지표 | 결과 |
|---|---|
| 주문금액과 상품단가의 상관계수 | **0.0008** |
| `금액 = 단가 × 수량`이 성립하는 비율 | **0.38%** |

**아무 관계가 없다.** 이 데이터의 `order_amount`는 상품 단가와 독립적으로 생성되어 있다.
→ 금액 검증·복원에 사용할 수 없다. 금액 오염은 값 자체의 규칙(음수·0·결측)으로만 판정한다.

### 4-2. 음수 값을 환불로 해석하기

`order_amount < 0`, `quantity = -3`을 환불 기록으로 볼 수 있는지 `status`와 교차 검증했다.
두 경우 모두 상태 분포가 전체 평균과 동일해서 **환불과 무관한 무작위 오염**으로 확인됐다. (근거는 3-2, 3-3 참고)

| 컬럼 | 설명 |

**원본 보존 컬럼을 두는 이유**
CRM과 같은 원칙이다. 값을 NULL로 바꾼 건이 많으므로(금액 25,798건, 날짜 72,090건), 무엇이 어떤 원본값에서 비워졌는지 테이블 안에서 바로 확인할 수 있어야 한다.

```sql
-- 날짜가 비워진 주문의 원본값 확인
SELECT date_flag, order_date_raw, COUNT(*)
FROM   orders
WHERE  order_date IS NULL
GROUP  BY 1, 2;
```

## 6. 처리 방침 요약

| 방침 | 적용 대상 | 근거 |
|---|---|---|
| **자동 수정** | 공백·대소문자·특수문자, 결제수단/상태 축약형, `five`→5, `2.0`→2 | 복원 결과가 유일하게 결정됨 |
| **NULL 처리** | 금액 상수 3종(`0`/`1,200`/`-50`), 음수·0·공백 수량, 비표준 날짜 4종 | 유지하거나 변환하면 집계가 왜곡됨 |
| **행 삭제** | **없음** | 한 컬럼이 깨져도 다른 컬럼은 분석에 쓸 수 있음 |
| **원본 보존** | 금액·날짜·수량 | NULL 처리 건이 많아 추적이 필수 |

> **원칙** : 확신 없이 지우지 않는다. 지우는 대신 표시하고 근거를 남긴다.
> **거래 데이터에서 추가되는 원칙** : 형식이 복원 가능하다는 것과 값이 진실이라는 것은 다르다.
> 복원했을 때 집계가 왜곡된다면, 복원하지 않고 비우는 편이 낫다.
