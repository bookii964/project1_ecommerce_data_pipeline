# 이커머스 데이터 정제 및 분석 파이프라인

> 오염된 원본 CSV 5종(93만 행)을 정제해 PostgreSQL 관계형 데이터베이스로 구축하고,
> SQL로 비즈니스 분석을 수행한 프로젝트.
>
> **사용 도구** : Python(pandas) · PostgreSQL · DBeaver · VSCode
> **작업 규모** : 원본 5개 파일 → 정제 스크립트 22개 → DB 테이블 6개 → 분석 쿼리 15개

---

## 1. 문제 정의

실무 데이터는 깨끗하게 오지 않는다. 이 프로젝트의 원본 데이터에는 다음이 섞여 있었다.

- 기본키 중복 (고객 1,734명이 중복 등록)
- 같은 값의 다섯 가지 표기 (`payment` / `PAYMENT` / `pay` / `paym3nt` / `tnemyap`)
- 날짜 형식 5종 혼재, 그중 3종은 값이 하나뿐인 시스템 대체값
- 한 칸에 여러 값이 들어간 컬럼 (제1정규형 위반)
- 형식은 정상이지만 의미가 없는 컬럼

**목표는 두 가지였다.**

1. 오염을 제거하되 **판단 근거를 남긴다.** 무엇을 왜 고쳤는지 추적할 수 있어야 한다.
2. 분석 가능한 관계형 구조로 만든다. 조인이 성립하고 제약조건이 유지되어야 한다.

## 2-1. 이 저장소에 데이터 파일이 없는 이유

**원본 CSV와 정제본 CSV는 저장소에 포함하지 않았다.** 스크립트·문서·SQL만 올라가 있다.

### 이유 ① 개인정보 형태의 데이터다

원본은 학습용 합성 데이터지만, 컬럼 구성은 실제 고객 정보와 동일하다.

```
이름 / 이메일 / 전화번호 / 생년월일 / 주소 / 도시 / 국가
```

합성 데이터라는 사실은 **저장소를 보는 사람에게 즉시 전달되지 않는다.** 공개 저장소에 5만 명분의 이메일과 전화번호가 올라가 있는 상태 자체가 부적절하다고 판단했다.

특히 아래 파일들은 개인정보를 그대로 담고 있어 제외 대상이다.

| 파일 | 내용 |
|---|---|
| `04_reports/삭제행_crm.csv` | 중복으로 삭제한 1,800명의 전체 행 |
| `04_reports/변경이력_*.csv` | 변경 전/후 값 (원본 이름·이메일 포함) |
| `02_profiling/*/이상데이터_상세.csv` | 오염 값 전수 |
| `03_cleaned/crm_customers_cleaned.csv` | 정제본 + 원본 보존 컬럼(`_raw`) |

### 이유 ② 용량 제한

`clickstream_500k_events.csv`는 122MB로 GitHub 단일 파일 한도(100MB)를 초과한다.

### 재현 방법

원본 데이터를 `01_raw/` 에 넣고 9절의 실행 순서를 따르면 동일한 결과가 재현된다.
스크립트는 파일 존재 여부·인코딩·컬럼 구성을 먼저 점검하므로(`18_preflight_check.py`),
데이터가 준비되지 않았다면 실행 시점에 알려준다.

## 2-2. 개인정보 취급 원칙

이 프로젝트에서 개인정보를 다룬 방식이다. 정제 과정에도 동일한 원칙을 적용했다.

### 분석 사본과 운영 마스터를 분리한다

| 계층 | 파일 | 수정 |
|---|---|---|
| 운영 마스터 | 원본 CSV | **금지** — 본인 확인·연락에 사용 |
| 분석 사본 | 정제본 CSV | 표준화 허용, 추적 가능해야 함 |

정제본은 **분석 전용**이다. 고객 응대·본인 확인·메일 발송에는 원본 또는 `_raw` 컬럼을 사용해야 한다. 이 내용은 DB 테이블 주석에도 기록되어 있다.

### 고친 것과 고치지 않은 것을 구분한다

이름·이메일은 고객이 직접 입력한 값이므로 임의 수정이 허용되지 않는다. 그럼에도 일부를 복원한 근거는 **오염이 시스템에서 발생했다는 정황**이다.

- `KKeevvin` 의 이메일이 `kevin.cantu***@` — 입력 시점에는 `Kevin` 이었다는 정황
- 특수문자가 `! * @` 3종만, 항상 마지막 위치에, 균등한 비율로 등장 — 사람의 입력 패턴이 아니다

반면 **대소문자 통일과 전화번호 형식 변경은 우리 판단이 개입한 가공**이다. 이 구분을 `데이터사전_crm.md` 0절에 명시했다.

### 원본을 같은 행에 보존한다

```sql
-- 값이 수정된 고객만 조회
SELECT customer_id, first_name_raw, first_name
  FROM crm_customers
 WHERE first_name <> first_name_raw;
```

### 문서의 예시 값은 마스킹한다

문서에 등장하는 이메일·이름 예시는 마스킹했다. 오염 패턴 예시(`KKeevvin`, `Tho8mas`)는 설명에 필요하므로 유지했다.

## 3. 작업 방법 — 5단계 정제 절차

파일마다 아래 절차를 반복했다. 단계를 나눈 이유는 **관찰과 수정을 분리**하기 위해서다.

| 단계 | 하는 일 | 산출물 |
|---|---|---|
| 1. 프로파일링 | 컬럼별 값 분포·결측·고유값 관찰. **수정하지 않는다** | 프로파일링 리포트 |
| 2. 규칙 정의 | "무엇이 정상인가"를 문서로 확정 | **데이터 사전 5종** |
| 3. 색출 | 규칙 위반 건을 전수 추출하고 유형 태깅 | 이상데이터 상세·집계 |
| 4. 정제 | 값 수정 및 새 파일 생성. 변경 이력 기록 | 정제본 CSV + 정제 로그 |
| 5. 검증 | 규칙 준수를 항목별로 합격/불합격 판정 | 검증 결과 + 전후 비교표 |

**원본은 절대 수정하지 않는다.** 이 원칙 덕분에, 작업 중 엑셀이 CSV 인코딩을 CP949로 변조해 스크립트가 실패했을 때 정제 스크립트 재실행 한 번으로 복구할 수 있었다.

### 정제 방침 5가지

| 방침 | 적용 기준 |
|---|---|
| 자동 수정 | 복원 결과가 **유일하게** 결정되는 경우 |
| 계산 복원 | 다른 컬럼을 근거로 복원 가능하고, 그 근거를 검증한 경우 |
| NULL 처리 | 값이 논리적으로 불가능하거나, 유지하면 집계가 왜곡되는 경우 |
| 유지 + 플래그 | 정답을 알 수 없는 경우 |
| 처리하지 않음 | 처리 이득이 없음을 검증한 경우 |

> **핵심 원칙** : 확신 없이 지우지 않는다. 지우는 대신 표시하고 근거를 남긴다.

## 6. 판단이 필요했던 지점

이 프로젝트에서 가장 시간을 쓴 부분이다. 각 판단은 데이터로 검증한 뒤 확정했다.

### 6-1. 이름 복원 — 알고리즘 3종을 비교하고 선택

`KKeevvin` → `Kevin`으로 만들려면 반복 글자를 줄이면 된다. 문제는 `Aaron`, `Lee`처럼 반복이 정상인 이름이 있다는 것.

이메일이 `firstname.lastname@` 형식이라 정답 대조가 가능했다.

| 방법 | 이메일과 일치율 |
|---|---|
| 아무것도 안 함 | 90.0% |
| **반복을 무조건 줄이기** | **75.9% (악화)** |
| 반복쌍 2개 이상만 줄이기 | 92.5% |
| **이메일과 대조해서 줄이기** | **92.8% (채택)** |

무조건 줄이면 정상 이름 8,452건의 일치율이 **93.1% → 0.0%**로 붕괴했다.

### 6-2. 처리 순서 — 순서가 결과를 바꾼다

`Melissa P***`과 `Melissa P***`은 컴퓨터에게 다른 값이다.

| 처리 순서 | 발견되는 중복 |
|---|---|
| 표기 통일 **전** 중복 제거 | 1,021건 |
| 표기 통일 **후** 중복 제거 | **1,789건** |

순서를 잘못 잡으면 중복 고객 768명이 남는다.

### 6-3. 날짜 복원 — 같은 발상, 다른 결론

두 파일에서 "다른 컬럼으로 날짜를 복원할 수 있는가"를 검토했다. 결론이 정반대였다.

| | orders | support_tickets |
|---|---|---|
| 검증 대상 | 금액 = 단가 × 수량 | 해결일시 − 접수일시 = 처리시간 |
| 검증 결과 | 상관계수 **0.0008** | 오차 **0.0000 (100% 일치)** |
| 결론 | **기각** — 복원 불가 | **채택** — 12,626건 복원 |
| 사용 가능 비율 | 70.0% | 49.0% → **91.0%** |

**같은 방법을 시도했고, 데이터가 뒷받침하는 쪽만 채택했다.**

### 6-4. 복원 가능해도 하지 않은 경우

orders의 `2024/31/01` 18,110건은 형식만 보면 `2024-01-31`로 변환할 수 있다. 그러나 변환하면:

| 지표 | 값 |
|---|---|
| 정상 데이터 하루 평균 주문 | 287.7건 |
| 실제 일별 최대 | 343건 |
| 변환 시 2024-01-31 주문 | **18,395건 (평균의 63.9배)** |

월별 추이·계절성·성장률 분석이 전부 무의미해진다.

또한 오염이 무작위인지 확인했다. 카이제곱 검정 결과 `p-value 0.6452`로, 날짜 오염 그룹과 정상 그룹의 주문 상태 구성비에 차이가 없었다. **오염이 무작위이므로 남은 70%로 분석해도 표본이 편향되지 않는다**는 근거가 됐다.

> 형식이 복원 가능하다는 것과 값이 진실이라는 것은 다르다.

### 6-5. 처리하지 않기로 한 결정

담당자명의 경칭(`Jr.`, `DDS`, `MD`) 719건을 제거하려 했다. 근거는 "같은 사람이 경칭 유무로 갈려 실적이 쪼개진다"였다.

**확인해보니 그런 사례가 0건이었다.**

| 검사 | 결과 |
|---|---|
| 경칭 상태가 2가지 이상인 이름 | **0건** |
| 경칭 유지 시 담당자 수 | 359명 |
| 경칭 제거 시 담당자 수 | **359명 (동일)** |

이득이 0이고 동명이인 충돌 위험만 있어 **규칙을 철회했다.**

> "이 처리가 필요하다"는 전제 자체도 검증 대상이다.

### 6-6. 개인정보 취급 — 분석 사본과 운영 마스터의 분리

이름·이메일·전화번호는 고객이 직접 입력한 개인정보다. 임의 수정은 원칙적으로 허용되지 않는다.

| 계층 | 수정 |
|---|---|
| 운영 마스터 (원본) | **금지** — 본인 확인·연락에 사용 |
| 분석 사본 (정제본) | 표준화 허용, 추적 가능해야 함 |

정제본에 **원본 값 보존 컬럼**을 두어 같은 행에서 대조할 수 있게 했다.

```sql
SELECT customer_id, first_name_raw, first_name
  FROM crm_customers WHERE first_name <> first_name_raw;
```

오염이 시스템에서 발생했다는 근거도 확보했다. `KKeevvin`의 이메일이 `kevin.cantu@`라는 점, 특수문자가 `! * @` 3종만 항상 마지막 위치에 균등하게 나타난 점은 사람의 입력 패턴이 아니다.

## 7. 시행착오 기록

실패와 그 진단 과정을 별도 문서로 남겼다. `04_reports/작업기록_clickstream_적재.md`

### clickstream 적재 — 두 번 실패한 이유

| 회차 | 결과 | 원인 |
|---|---|---|
| 1차 | 실패 (0행) | `device_id` 뒤쪽 공백 9,915건 |
| 2차 | 실패 (0행) | `device_id` 형식 오염 10,016건 |
| 3차 | **성공 (500,000행)** | — |

**근본 원인은 `device_id`를 "분석에 쓸 수 없는 컬럼"으로 판정한 뒤 형식 검사를 생략한 것이다.**

> '분석에 쓰지 않는 컬럼'과 '검사하지 않아도 되는 컬럼'은 다르다.
> 적재 대상인 모든 컬럼은 최소한 형식 검사를 거쳐야 한다.

정제 스크립트만 고치지 않고 **3단계 색출 스크립트에도 검사를 추가**해, 앞으로는 검출 단계에서 잡히도록 했다.

### page_url 오염을 놓쳐 파생 컬럼이 부정확했던 사례

`page_url`은 "값을 수정하지 않는다"고 결정한 컬럼이었다. 그래서 오염 조사를 소홀히 했는데, **그 컬럼에서 `product_id`를 파생하고 있다는 점을 놓쳤다.**

5단계 검증에서 URL 고유값이 3,020 → 3,019로 거의 줄지 않은 것을 보고 전수 조사했더니 오염이 5종류였다.

| 유형 | 건수 | 영향 |
|---|---|---|
| 끝 슬래시 중복 | 8,231 | 같은 페이지가 다른 URL로 집계 |
| **전부 대문자** | 8,482 | **product_id 추출 실패 6,363건** |
| 스킴 슬래시 과다 | 8,298 | 표기 불일치 |
| 스킴 누락 | 8,195 | 표기 불일치 |
| **경로 축약** | 6,213 | **product_id 추출 실패 6,213건** |

정규화 후 `product_id` 추출이 **356,366 → 368,942건**으로 늘었다. 상품 조회 이벤트의 3.4%를 되찾았다.

재발 방지로 검증 항목을 추가했다. **URL에 상품 코드가 있는데 `product_id`가 비어 있는 행이 0건인지** 확인한다.

> 값을 수정하지 않기로 한 컬럼이라도, 그 컬럼에서 파생 컬럼을 만든다면 오염 조사를 해야 한다.
> `device_id`를 '사용 금지'로 판정한 뒤 형식 검사를 생략해 적재가 실패한 것과 같은 구조의 실수다.

### 검증 쿼리가 틀린 사례

`product_id` 추출 검증에서 6,163건이 오류로 나왔다. 실제 값을 확인하니 `.../product/PROD-0187///` 처럼 URL 끝에 슬래시가 붙은 것이었고, **추출은 정확하고 검증 조건이 과도하게 엄격**했다.

> 검증에서 오류가 나오면 데이터를 의심하기 전에 검증 조건을 먼저 확인한다.

이 오탐 덕분에 URL 표기 오염(3,020종 → 2,516종)을 발견했다.

### 인코딩 충돌

엑셀로 정제본 CSV를 확인하고 저장했더니 UTF-8이 CP949로 변조되어 후속 스크립트가 실패했다.

- **복구** : 원본 불변 원칙 덕분에 정제 스크립트 재실행으로 해결
- **재발 방지** : 모든 스크립트에 인코딩 자동 감지 로직 추가
- psql 실행 시 `chcp 65001` + `PGCLIENTENCODING=UTF8` 필요

## 10. 이 프로젝트에서 얻은 것

**① 정제는 코드가 아니라 판단이다**
`str.replace()`를 쓰는 것은 어렵지 않다. 어려운 것은 "이 값을 고쳐도 되는가"를 정하는 일이다. 이름 복원 알고리즘 비교, 날짜 복원 채택·기각, 경칭 규칙 철회는 모두 데이터로 검증한 뒤 결정했다.

**② 추적 가능성이 신뢰를 만든다**
정제 결과물보다 중요한 것은 "무엇을 왜 바꿨는지"다. 변경 이력, 삭제 행 보관, 원본 값 보존 컬럼, 처리 사유 플래그를 모두 남겼다. 그 덕분에 분석 단계에서 "이상치 포함/제외" 두 기준을 모두 계산할 수 있었다.

**③ 검증은 독립적이어야 한다**
Python 검증과 DB 제약조건은 서로 다른 방식이다. 한쪽을 통과해도 다른 쪽에서 걸릴 수 있고, 실제로 clickstream 적재에서 두 번 걸렸다. 엄격한 자료형과 제약조건은 적재를 어렵게 만드는 대신 오염을 찾아준다.

**④ 없는 결론을 쓰지 않는다**
분석에서 대부분의 항목에 유의한 차이가 없었다. 그것을 그대로 기록했다. "문의 많은 고객 = 우량 고객"이라는 그럴듯한 해석은 지표를 분해해 기각했다.

## 11. 남은 과제

정직하게 밝히는 한계다.

- **session_id 사용 불가** — 세션 단위 퍼널·이탈률 분석이 불가능하다. 고객 단위로만 집계했다.
- **비로그인 이벤트 30% 제외** — 퍼널 분석은 `customer_id`가 필요해 이 부분이 빠진다.
- **테이블 간 기간 불일치** — clickstream은 3개월, 나머지는 2년이다. 조인 분석 시 기간을 맞춰야 한다.
- **지역 정보 신뢰도 낮음** — `state`(미국 50개 주)와 `country`(243개국)가 모순되어 분석 축으로 사용하지 않았다.
- **장바구니 페이지 이벤트를 퍼널에 넣지 않았다** — `page_type = 'cart'` 데이터가 3만 건 있지만, 이 이벤트가 `add_to_cart` 이후에 발생했는지 순서를 검증할 수 없다. 검증 없이 4단계 퍼널로 만들면 근거 없는 수치가 된다.
